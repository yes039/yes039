# 宣傳戰情室 v0.4（開發測試版）

主體是**我們自己在 FB 的整體宣傳**。首頁同時呈現兩條線：

- **A. 日常 FB 發文**：個人帳號、粉專、自有社團、他人社團四個發布主體的發文安排、執行進度與互動成效。
- **B. 付費廣告專案**：每個合作、自有課程或客戶是一個專案。「Jason 老師合作招生」是第一個付費專案；「玉欣珍會員活化」是另一個獨立專案。

日常貼文可以不掛專案，也可以選填「支援某專案」；專案頁把相關自然貼文與專用付費廣告分區呈現，兩者成效不相加。

**狀態：只在本機開發與測試，尚未部署。** 畫面上的貼文、專案與數字都是標示【測試】的程式產生資料，不是實際營運資料。正式部署、接入真實名單、投放廣告與發送訊息，等 Shen 確認後再執行。

| 投放波次、登錄與匯入、代碼與連結、資料來源、專案設定 | 沿用 v0.1 |

## 口徑

**發文數**（同一篇在同一欄最多算一次；同題材發到不同位置，每個位置各算一筆）

| 欄位 | 計算 |
|---|---|
| 預計發文 | 預定日期在期間內，且狀態不是「取消」 |
| 已發文 | 實際發布日期在期間內（不論預定哪天） |
| 待發文 | 預定日期在期間內、尚未發布、未取消；預定日已過者另標「逾期」 |
| 取消 | 預定在期間內但取消，不算入預計 |

**發文數核對**：預計＝依期發布＋期內預定、期外發布＋待發；已發＝依期發布＋跨期補發（期外預定、期內發布）＋臨時加發（沒有預定日）；取消另列。所以「已發＋待發」不一定等於「預計」。每個數字都能點進貼文清單看是哪幾篇，清單每篇標出歸類。

**互動**：第一版是「期間內實際發布的貼文，到各篇『統計截至』時間為止的累計互動」，人工登錄；不是期間內新增的互動。尚未登錄的貼文顯示「尚未登錄」，不以 0 計。

**花費**：本期花費（所選期間）、波次累計、素材累計、專案累計、預算分開標示。應有廣告資料的日子（依投放紀錄或波次期間）有任何一天缺資料時，花費標「已知小計」；累計花費缺資料時預算使用率顯示「至少 X%」，不當成完整總額。

**成果分組**：付費廣告成果（對應到付費素材）、免費引流成果（LINE、自然貼文等免費渠道）、來源不明（只對應到波次＋完全無法辨識）分開列；專案合計以人去重，可能小於各組相加。

**付費廣告成本**：每筆成本＝本期付費花費 ÷ 同期間可歸因至付費廣告素材的成果。免費引流與來源不明不進分母。花費或成果任一不完整時，正式成本顯示「暫不計算：廣告資料不完整」或「暫不計算：成果資料不完整」。

**招生進度**：本期新增報名跟隨週／月／自訂期間；累計報名＝專案開始至昨天（以人去重），累計達成率＝累計報名 ÷ 招生目標，不隨所選期間改變。累計報名資料不完整時，只顯示「已知累計報名 N 人／目標 M 人」與「資料不完整，達成率暫不計算」，不畫進度條；首頁與專案頁同一規則。報名目前**不扣除取消**（尚無取消報名紀錄類型）；付款與退款分開以筆數、金額呈現，退款不扣報名人數。

**投放建議**：已結束的素材與波次顯示「已結束」與歷史成效，不給投放指令；進行中的素材要資料完整、達到樣本門檻、設好目標成本，才給「持續／觀察／調整」，否則顯示「待補資料／暫不判斷」並列出依據。

**比率**：同一範圍的分子、分母加總後相除；滑鼠移到比率上會顯示「分子 ÷ 分母」。

**完整度**：最新日期與缺漏分開寫，例如「更新至 10/14・缺 10/12」。

**判斷**：花費、點擊或主要成果有任何一項不完整或缺資料時，不會給「持續」，並列出依據。

**分開不相加**：日常互動與招生成果分開；自然貼文上登錄的詢問與專案成果紀錄分開；Meta 後台回報不與自家紀錄相加；無法確認來源的成果列「來源不明」，不分配給任何素材。

## 哪些可用、哪些要人工、哪些待串接

| 項目 | 狀態 |
|---|---|
| 專案、波次、素材、投放紀錄、貼文、發布位置的新增與編輯 | 可操作 |
| 日曆、清單、單篇、素材比較、期間（本週／本月／曆月／近 7／近 30 天／自訂）切換 | 可操作 |

## 執行

```bash
npm install
npm test                          # 後端單元測試（28 項）
npm run dev                       # 本機伺服器 http://localhost:8787（記憶體資料庫，自動載入測試資料）
node scripts/e2e.mjs              # 介面操作測試（需先 npm run dev）
node scripts/screenshots.mjs      # 桌機與手機截圖到 screenshots/
npm run preview                   # 產生 preview/index.html：瀏覽器內執行同一套 API 與測試資料
```

## CSV 格式

**FB 廣告報表**：從 Meta 廣告管理員匯出、選「依天」細分。必要欄位：報告開始日期、廣告名稱、花費金額、曝光次數、連結點擊次數（支援中英文欄名；實際欄名待以真實匯出檔核對）。廣告名稱需以素材代碼開頭，例如 `JSN-2610-01-VD01-v1｜說明`。對應不到的列仍記錄花費，並列為待辦。

**成果紀錄**：`類型,日期,活動代碼,素材代碼,領取碼,數量,金額,外部編號,電話,Email,備註`。類型可填電子書領取、名單、有效名單、報名、付款、退款。有外部編號時重複匯入會覆蓋同一筆。

## 正式部署前檢查（尚未執行）

1. 建立 D1 資料庫並套用 `schema.sql`，把 `database_id` 寫入 `wrangler.toml`。
2. 設定 Cloudflare Access（Email 名單），填 `ACCESS_TEAM_DOMAIN`、`ACCESS_AUD`；未設定時 API 一律拒絕。
3. 設定 `ADMIN_EMAILS` 與 `wrangler secret put HASH_SALT`。
4. 用一份真實的 Meta 匯出檔核對欄名。
5. 不匯入測試資料；接入真實名單前確認各專案的資料使用範圍。

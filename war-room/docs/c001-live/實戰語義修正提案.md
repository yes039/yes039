# 實戰語義修正提案

> 起因：C001 現實戰況快照驗出兩個結構問題。
> 1. UNKNOWN（情報未確認）會被畫成 IDLE（已確認尚未開始）。
> 2. 節點依賴規則會抹掉已發生的事實（M002 v1 已存在，但上游「素材」未完成，引擎無法記錄）。
>
> 本提案修的是**戰役系統的語義**，不是 C001 特例。只提案，不實作。

---

## 0. 核心判斷：把三件混在一起的事拆開

目前引擎只有一個欄位（節點狀態）同時承擔了三種意思：

| 層 | 問的問題 | 例子 |
|---|---|---|
| **情報** | 我們知不知道這個節點的現況？ | 招生目標：不知道名額 |
| **事實** | 這個節點已經產出了什麼？ | 製片：M002 v1 檔案已存在 |
| **進度** | 這個節點在流程中走到哪一格？可不可以交棒？ | 製片：還不能交貨 |

V2 的三條鐵律管的是「進度」。這兩個問題的根源，是「情報」和「事實」沒有自己的位置，只能硬擠進「進度」裡。

**修正方向：** 進度規則一條都不放鬆，另外給情報和事實各自正式的表達方式。

---

## 1. UNKNOWN 該進引擎，還是只放在顯示層？

**建議：進引擎，成為正式狀態。但它的定位是「情報狀態」，不是進度的一格。**

### 為什麼不能只放在顯示層
引擎會根據狀態算出很多東西：誰 READY、下一棒是誰、交貨進度、戰役是否 COMPLETE、底部計數。如果 UNKNOWN 只是畫面上的貼紙，引擎內部仍然會把它當成 IDLE 來計算：
- 下一棒可能指向一個其實早就做完、或根本不存在的節點；
- 「尚未開始」的計數會把不知道的節點算進去；
- 畫面上的貼紙和引擎算出的結論互相矛盾，指揮官看不出哪一個才對。

也就是 UNKNOWN 必須參與計算，才能保證所有推算結果都不會把「不知道」當成「確定」。

### UNKNOWN 的規則
| 規則 | 內容 |
|---|---|
| 何時出現 | 只有**實戰模式**開戰時，作戰節點的起點是 UNKNOWN。演練模式維持 V2：IDLE／READY |
| 怎麼離開 | 只能透過新的「回報」事件（見第 5 節），附證據，轉成任何一個已確認的狀態 |
| 作戰指令 | 對 UNKNOWN 節點送 STARTED／DONE 等指令一律拒絕：「情報未確認，請先回報現況」 |
| 依賴 | UNKNOWN **永遠不算** DONE，不能解鎖任何下游 |
| 戰役完成 | 戰役完成條件裡的節點只要有一個 UNKNOWN，戰役就不能 COMPLETE |
| 計數 | 底部與手機摘要多一格「UNKNOWN」，不併入 IDLE |
| 顯示 | 灰色、問號、標示 UNKNOWN，和 IDLE 的實線暗框明顯不同 |

**IDLE 的定義跟著收緊：** IDLE＝「已確認尚未開始」。只有回報或推算能確認時才會出現。

## 2. 如何同時表達「素材 WAITING」與「M002 v1 草稿已存在」

**建議：新增「事實紀錄」，掛在節點上；再把連線分成不同強度（第 3 節）。**

### 2a. 事實紀錄（evidence / facts）
- 每個節點可以附加一條條事實：`{內容, 證據來源, 時間, 回報人}`。
- 事實**只能追加，不改變進度狀態**，也不解鎖任何下游。
- 畫面顯示在節點副標或摘要裡，例如：「v1 草稿已存在 · E1」。

### 2b. 套用到 M002
| 節點 | 進度 | 事實 | 說明 |
|---|---|---|---|
| 素材 | WAITING（等報名資訊） | — | 證據 E5 |
| 製片（委派海豹 M002） | ACTIVE | 「v1 草稿已存在」E1、E2 | 允許先開工（第 3 節的「交付閘」）；**不能交貨**，畫面自動標出原因「交貨被擋：上游 素材 未 DONE」 |
| M002 內部 · 成片輸出 | DONE（v1） | E1 | 海豹任務自己的事實 |
| M002 內部 · 成片核可 H4 | UNKNOWN | — | 合併 PR 不等於核可 |

這樣「v1 已存在」和「素材還在等」就能同時成立，彼此不衝突，正式交貨也仍然被擋住。

## 3. 哪些連線是 hard dependency，哪些只是 workflow／order

**建議：連線加上一個可選的「強度」，分三種。不寫就是 hard，等同 V2 現行規則。**

| 強度 | 上游未 DONE 時，下游可以… | 用在什麼情況 |
|---|---|---|
| **hard**（預設） | 不能開工，也不能完成 | 下游**實體上需要上游的產出**才能開始。例：沒有成片就無法審核 |
| **finish**（交付閘） | **可以先開工、產出草稿**；但不能完成或交貨 | 下游可以先做，但正式版需要上游。例：影片可先做，正式版需要報名資訊 |
| **order**（流程順序） | 不擋任何事；只表示建議順序與光流方向 | 慣例上的先後，實際上可以平行。例：招生名額未定，也能先確定受眾 |

### C001 連線的建議分類（示範，寫在 C001 Config 裡；core 不認得任何 C001 節點）

| 連線 | 建議 | 理由 | 確定度 |
|---|---|---|---|
| 招生目標 → 受眾 | **order** | 受眾可以在名額、價格未定前確定（M002 已證明） | 建議 |
| 戰果庫 → 受眾 | resource（現狀） | 資料參考 | — |
| 受眾 → 策略 | hard | 沒有對象就無法定訊息 | 建議 |
| 策略 → 企劃 | hard | 企劃依策略展開 | 建議 |
| 企劃 → 配兵 | hard | 先有企劃才知道要派誰 | 建議 |
| 配兵 → 素材 | **order** | 報名資訊由你（H1）提供，不需要先派兵 | 建議 |
| 素材 → 製片 | **finish** | 影片可先做草稿；正式版需要報名資訊 | 建議 |
| 製片 → 審核 | hard | 沒有正式版就無從審核 | 建議 |
| 審核 → 發布／投放 | hard | 未審不發 | 建議 |
| 發布／投放 → 名單／報名 | **待你確認** | 若名單只算「這次投放帶來的」→ hard；若口碑名單也算 → order | 需確認 |
| 名單／報名 → 戰果 | finish | 戰果可邊收邊算，但最終結算要等報名截止 | 建議 |
| 戰果 → 寫回戰果庫 | hard | 先有戰果才寫回 | 建議 |

**判斷準則（通用，未來任何戰役都適用）：**
- 下游**開工**就需要上游的產出 → hard
- 下游可以先做，但**正式完成**需要上游 → finish
- 只是習慣的順序 → order

## 4. 如何保持 V2 三鐵律，又不否認現實

**關鍵：分清楚兩種事件。**

| 事件種類 | 意思 | 規則 |
|---|---|---|
| **作戰指令**（V2 現有：STARTED／WAITING／RESUMED／APPROVED／DONE／FAILED） | 「現在要推進這一格」 | 照 V2 規則嚴格檢查，不合法就拒絕。**完全不放鬆** |
| **現況回報**（新增：REPORTED） | 「現實中這件事已經發生了」 | 現實不能被拒絕：一定會被記錄。但回報**不能跨過閘門造出 DONE** |

### 三鐵律逐條對照
| 鐵律 | 修正後怎麼守 |
|---|---|
| **路過 ≠ 完成** | 不變。回報只作用在被指名的節點，而且必須附證據；不會往上下游擴散。事實紀錄永遠不會讓節點 DONE |
| **異常可原地恢復** | 不變。另外多一條恢復路徑：UNKNOWN → 回報 → 已確認狀態 |
| **未完成上游不得跳步** | 改寫得更精確：「**不得跨過未完成的 hard／finish 閘門去完成或交棒**」。作戰指令照舊拒絕。回報若想把節點報成 DONE、但閘門未開，系統會把它記成「ACTIVE＋事實紀錄」，並標出「完成被擋：上游 X 未 DONE」；不會產生假 DONE，也不會讓下一棒提前出現 |

### 回報碰到閘門時的處理
| 回報內容 | 閘門狀況 | 結果 |
|---|---|---|
| 某節點 DONE | 閘門都已開 | 記為 DONE（附證據） |
| 某節點 DONE | 有 hard／finish 閘門未開 | 記為 ACTIVE＋事實「已有成果」＋標記「完成被擋：上游 X」 |
| 某節點 ACTIVE／WAITING | 有 **hard** 閘門未開 | 照實記錄，但標記「越序：上游 X 未 DONE 即已開工」，讓指揮官看見現實與流程的落差 |
| 某節點 ACTIVE／WAITING | 只有 finish／order 閘門未開 | 照實記錄，不標異常（這是允許的） |

**結論：** 現實會全部進入戰情室；但「正式完成、交棒、戰役 COMPLETE」仍然只能照規則發生。

## 5. 最小修改方案

### 5a. Config（全部可選，不填＝ V2 現行行為）
1. 連線可加第三個欄位表示強度：`["mat", "prod", "finish"]`；不寫就是 `hard`。
2. 不新增其他欄位。

### 5b. 引擎
1. 新增狀態值 **UNKNOWN**：只在 `TASK_CREATED({mode: "live"})` 時作為作戰節點起點；演練模式不受影響。
2. 新增事件 **REPORTED**：`{node, state?, fact?, evidence, by, at}`。
   - `state` 可省略，表示只追加事實；
   - 依第 4 節表格處理閘門；
   - 對資源節點、委派節點的處理沿用現有規則（委派節點仍只能由 Mission 推算）。
3. 每個節點新增**事實清單**（只能追加）。
4. 開工、完成檢查改成依連線強度判斷：開工看 hard，完成看 hard＋finish，order 不擋。
5. UNKNOWN 不算 DONE、不能解鎖下游；戰役完成條件含 UNKNOWN 時不能 COMPLETE。
6. 委派節點的推算規則加一條：交貨範圍內有 UNKNOWN 時，摘要標「部分情報未確認」。

### 5c. 顯示
1. UNKNOWN 的樣式：灰色、問號、標示 UNKNOWN；計數多一格。
2. 節點副標或摘要顯示事實，例如「v1 草稿已存在」。
3. 自動產生的原因文字：「完成被擋：上游 X 未 DONE」「越序：上游 X 未 DONE 即已開工」。

### 5d. 不做
- 不新增 BLOCKED 狀態：「被上游閘門擋住」用自動原因文字表達即可。
- 不改兵陣 layout、不改 V3.1 邏輯、不改手機架構。
- 不 hard-code 任何 C001 節點：core 只認得「連線強度」「UNKNOWN」「REPORTED」「事實」四個通用概念。

### 5e. 相容性與驗收（實作時）
- 所有既有 Config 不填連線強度、所有演練不用 live 模式 → V2 A/B/C、SEAL、V3 六項、下鑽 41 項、手機 14 項應**原樣通過**。
- 新增驗收（通用規則，以 C001 為案例）：
  1. live 開戰後，12 個作戰節點全部是 UNKNOWN，計數不併入 IDLE；
  2. 對 UNKNOWN 節點送作戰指令被拒；
  3. 回報「受眾 DONE」在 `招生目標 → 受眾` 為 order 時成立；改成 hard 時，被記為 ACTIVE＋事實＋「完成被擋」；
  4. 素材 WAITING 時，製片可以有「v1 已存在」事實並為 ACTIVE，但交貨被擋、審核不會 READY；
  5. 回報「製片 DONE」不會產生假交貨；
  6. 戰役在任何 UNKNOWN 未解除前不能 COMPLETE；
  7. 「路過 ≠ 完成」檢查仍為 0 筆。

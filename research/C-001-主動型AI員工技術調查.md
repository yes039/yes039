## 結論先講：還差哪幾個關鍵零件

「主動型 AI 員工」= **資料進得來 → 定時自己去看 → 看得懂 → 判斷要不要叫人 → 叫得到人 → 人點頭後才動手 → 事後驗收**。
我們現在有 AI 的「腦」（Claude API 已接通）和「看得懂」的能力，也有一套可沿用的雲端底座（FB 內容工作室 V5：Cloudflare Workers＋D1，已上線）。缺的是下面 6 個零件：

| # | 缺的零件 | 現況 | 補法（MVP） |
|---|---|---|---|
| 1 | **現場資料入口**：師傅／主任每天用手機回報 | 無。T01 試跑表還在手填階段 | LINE 官方帳號＋Webhook（傳文字、照片、語音） |
| 2 | **狀態資料庫**（AI 的「工作記憶」） | V5 的 D1 只有貼文、表單、名單 | D1 新增工地、回報、事件、授權四張表；照片放 R2 |
| 3 | **排程器**（「定時巡視」） | V5 Worker 沒有設定 Cron | Workers Cron Trigger（例如 17:45 查缺交、20:00 產日摘要） |
| 4 | **異常判斷規則＋AI 判讀的驗收樣本** | 沒有規則，也沒有標註過的範例 | 先寫死 5–8 條規則；用 T01 試跑資料當驗收樣本 |
| 5 | **通知＋授權通道**（老闆手機一鍵批准） | 無 | LINE 推播＋按鈕（postback）→ 寫入授權紀錄 |
| 6 | **驗收迴圈與稽核**（事情有沒有真的辦完） | 戰果庫、契約都靠人工複製貼上 | 事件狀態機（開立 → 已通知 → 已授權 → 已完成 → 已驗收）＋儀表板 |

**最關鍵的不是技術，而是零件 1：現場的人願不願意每天回報。**這一點要先用已設計好的 T01 人工試跑驗證（閘門 G0：回報率 ≥ 60% 且老闆覺得摘要有用 ≥ 2 天），再寫程式。

Claude 官方的「主動型」產品（Claude Duet）確實存在，但**目前只開放給美國的 Pro／Max 個人帳號**，不支援 LINE、不能發簡訊，所以**不能當作台灣中小企業產品的底座**。它可以拿來當我們自己內部的參考設計，產品要自己組。

### 哪些環節用傳統程式，哪些真正需要 AI

| 環節 | 主要技術 | 為什麼 | AI 的角色 |
|---|---|---|---|
| 企業資料進來 | **傳統**：LINE Webhook、表單 | 收訊息不需要智慧 | 無 |
| 把回報轉成結構化資料 | **AI** | 師傅寫「三樓灌漿完成，明天缺 2 分鋼筋 30 支」這種自由文字或語音，傳統程式很難穩定拆解 | 抽出工項、進度、缺料、人數、異常；看照片描述現場 |
| 定時巡視 | **傳統**：Cron | 時間到就跑，不需要判斷 | 無 |
| 異常判斷 | **先規則，後 AI** | 「17:30 還沒回報」「進度落後超過 X 天」「回報裡有缺料欄」用規則判斷最準、最便宜、可解釋 | 只處理規則抓不到的語意異常（業主抱怨、漏水、工安疑慮），並且要附上原文依據 |
| 通知老闆 | **傳統**：LINE 推播 | 送達要可靠 | 寫一頁摘要、排出輕重緩急 |
| 授權執行 | **傳統**：按鈕、狀態機、稽核紀錄 | 誰在幾點批准什麼，必須可追溯 | 可以準備執行草稿（例如叫料訊息），但不能自己送出 |
| 結果驗收 | **規則為主** | 「期限內有沒有標成完成、有沒有照片」可以用規則判斷 | 比對完成照片與原始異常、寫結案摘要（需要人確認） |

原則：**AI 只放在「看懂非結構化內容」與「寫給人看的文字」這兩個地方**，其他都用確定性的程式。這樣成本低、可除錯，也能對老闆解釋「為什麼通知你」。

## 四、營造公司 MVP：一個工地（Q4）

> 案例設定：營造公司管理 9 個工地，先挑 1 個做 MVP。雲端硬碟裡的 F03 水電訪談表是以「八工地」設計的，兩個案例可以共用同一套 MVP。

### 4-1 最小技術組合

| 元件 | 選擇 | 理由 |
|---|---|---|
| 回報入口 | LINE 官方帳號（輕用量方案）＋Messaging API | 現場人員本來就用 LINE（F01 的 B7、D1 會確認）；不用裝新 App |
| 後端 | 沿用 V5 的 Cloudflare Workers＋D1；新增 R2 存照片 | 已部署、團隊熟悉、已有 Secret 管理與 Claude 呼叫；不用再開新平台 |
| 排程 | Workers Cron Trigger（免費方案每個帳號 5 個） | V5 目前 0 個，夠用 |
| AI | Claude API：Sonnet 5.5 負責抽取與判讀，Haiku 5.5 負責簡單分類（可選） | 與 V5 同一把 API Key 與計費 |
| 通知與授權 | LINE 推播＋按鈕 | 老闆不用學新工具 |
| 儀表板 | Worker 輸出一頁手機版網頁（比照 V5 的 `app-html`），沿用 V5 的登入機制 | 不用另外買 BI 工具 |

### 4-2 操作流程（每天）

| 時間 | 誰 | 做什麼 | 系統 |
|---|---|---|---|
| 收工前（例：17:00–17:30） | 主任或師傅 | 在 LINE 傳 1 段文字或語音＋2–4 張照片（今日完成、明日計畫、缺料、人數、異常） | Webhook 收下 → AI 抽成固定欄位 → 回覆「已收到，缺：○○欄」請對方補 |
| 17:45 | 系統 | 巡視：沒回報 → 提醒回報人；欄位缺 → 追問一次 | Cron＋規則（不用 AI） |
| 20:00 | 系統 → 老闆 | 一則 LINE：工地狀態燈號＋3 行摘要＋需要決定的事（按鈕：批准、退回、明天再說） | 規則＋AI 摘要 |
| 隨時 | 系統 → 老闆 | 重大異常（工安、停工、業主客訴）立即推播 | 規則觸發；AI 只負責分類並附原文 |
| 老闆按鈕 | 老闆 | 批准叫料或交辦 → 系統記錄並通知負責人 | 狀態機＋稽核紀錄 |
| 隔天回報 | 主任 | 回報交辦事項的結果 | 驗收規則：期限內完成且附照片 → 結案 |

- 每天 AI 輸入約 18,000 tokens（含規則、提示詞、近期紀錄），輸出約 3,000 tokens
- 匯率以 1 USD ≈ 32 TWD 粗估（未查證當日匯率）

### 4-4 主要風險

| 風險 | 程度 | 緩解 |
|---|---|---|
| **現場不回報**（最大風險） | 高 | 先跑 T01，沒通過 G0 就不開發；回報設計成 1 分鐘以內；老闆要把回報當作規定 |
| AI 抽錯欄位或誤判異常 | 中 | 規則優先；AI 判讀一定附原文；用試跑資料建立 20–30 筆驗收樣本，每次改提示詞都要重跑 |
| 漏報急事（排程之間發生的事） | 中 | 重大事件靠回報當下即時判斷（Webhook 直接觸發），不等 Cron |
| 資料外洩、業主保密要求 | 中 | F01 的 J1–J5 同意書先簽；只存代號；F03 C10 先問清楚哪些資料不能上雲 |
| LINE 免費則數不夠或調價 | 低 | 回覆訊息免費，盡量用「回覆」代替「推播」；9 個工地時改中用量方案 |
| Meta、LINE 權杖到期 | 低 | V5 已有到期維護紀錄；比照建立權杖到期提醒 |
| 依賴研究預覽功能 | 中 | 客戶產品**不要**建在 Duet 或雲端排程任務上；只用正式版的 API |

## 五、部署方案比較（Q5）

| 方案 | 初期建置 | 每月營運費（1 個工地） | 維護難度 | 權限與安全 | 擴充成多客戶 | 判定 |
|---|---|---|---|---|---|---|
| **1. Claude 原生**（Duet、雲端排程任務） | 最低（設定即可） | 包含在訂閱內（Pro 或 Max），但吃用量額度 | 低 | ❌ 以個人身分執行；排程任務執行中不經批准就能用 Connector 寫入；Duet 只限美國 | ❌ 個人帳號、不能多租戶、沒有 LINE | **只適合內部戰隊**（例如 Y-001 每日巡視），不適合當客戶產品 |
| **2. Claude API＋一般雲端排程**（例：Google Cloud Scheduler＋Cloud Run） | 中 | API US$2–8＋雲端 US$0–10 | 中（多一個平台要學） | ✅ 自己控制 | ✅ | 可行，但我們已有 Cloudflare，沒必要再開一個平台 |
| **3. Claude＋GitHub Actions** | 低到中 | 私有 repo 有免費分鐘數；API 另計 | 中 | 🟡 Secrets 可用，但資料要另外存放；**yes039/yes039 是公開 repo，絕不能放企業資料** | 差 | 🟡 排程可能延遲，高負載時可能被丟棄（GitHub 官方說明）；最短 5 分鐘。只適合內部批次，不適合老闆通知 |
| **4. Claude＋Cloudflare Workers**（沿用 V5） | **低**（底座已存在） | **US$0–5＋API US$2–8** | 低到中（已有部署經驗與交接文件） | ✅ Secret 已在用；可加租戶隔離 | ✅ D1 可以每個客戶一個資料庫，或用欄位隔離 | **推薦** |

## 六、跨產業複製（Q6）

### 6-1 共用核心（做一次，三個產業都能用）

1. **回報入口**：LINE Webhook、文字、照片、語音
2. **資料模型**：據點（工地或門市）、人員角色、回報、事件、任務、授權、驗收
3. **排程與規則引擎**：規則用設定檔，不寫死在程式裡
4. **AI 抽取與判讀**：每個產業各一份欄位清單與提示詞（屬於「設定」，不用改程式）
5. **通知、授權、稽核**：LINE 按鈕與狀態機
6. **儀表板**與每日、每週摘要
7. **診斷工具組**（F01–F05、T01）：已經涵蓋水電與營造，餐飲要另做一版
8. 多客戶隔離、權杖與到期管理（V5 已有一半）

### 6-2 各產業專屬

| | 營造 | 水電 | 餐飲 |
|---|---|---|---|
| 據點 | 工地（9 個） | 工地（8 個，依 F03） | 門市 |
| 回報者 | 工地主任、工務 | 師傅、主任 | 店長、廚房 |
| 核心欄位 | 工項進度、出工人數、天候、機具、工安、監造意見 | 派工、點工、叫料、零星追加 | 營收、來客、食材進貨與報廢、缺貨、評論、排班 |
| 典型異常 | 進度落後、缺料停工、工安、估驗與進度對不上 | 缺料、追加施工沒收到錢、重複叫料 | 營收驟降、負評、食材報廢偏高、員工缺勤 |
| 外部資料 | 公共工程日報格式、PCCES（後期） | 材料行報價 | POS、Google 評論、IG／FB（已有 V5 與海豹小隊） |
| 客製化成本（推估 🟡） | 中高：日報格式可能是業主規定 | 中 | 低到中：欄位少、標準化程度高 |

### 6-3 客製化成本與商品化

- **每個新客戶的成本**：主要是導入人力（訪談 F01–F03、試跑 T01、調整規則），不是程式。目標是讓新客戶「只改設定，不改程式」。
- **單位成本**：每個據點每月約 NT$100–400 的雲端與 AI 費用（推估）。F01 的 H3 讓客戶勾選可接受月費（NT$1,000 以下／1,000–5,000／5,000–20,000），毛利空間存在，要用訪談結果驗證。
- **商品化路徑**：
  1. 顧問導入＋代管（1–3 家，邊做邊把規則設定化）
  2. 產業模板包（營造版、水電版、餐飲版）
  3. 自助設定（10 家以上才值得做）
- **差異化**：不是「有 AI」，而是「**現場回報率**＋**老闆每天只看一頁**＋**每個通知都有依據**」。這要靠導入方法（F 系列＋T01 閘門），工具很容易被抄。

## 七、執行建議

### 先做（依序）

1. **T01 人工試跑**（不寫程式）：挑 1 個工地，先跑 5 天基準期再跑 3 天試跑；由 C 每晚用 Claude 對話整理摘要給老闆。沒通過 G0 就停下來檢討回報設計，不要開發。
2. **補資料給 C**：Y-001／Y-002 職責卡、Airtable 結構、是否已有 LINE 官方帳號。
3. **規則版 MVP**：V5 的 Worker 加 Cron、LINE Webhook、D1 四張表，先只做「缺交提醒＋每晚彙整」，不用 AI。
4. **加 AI**：自由文字與照片轉欄位、語意異常、晚間一頁摘要；用 T01 資料當驗收樣本。
5. **加授權按鈕與驗收**，跑滿 2 週，看三個指標：回報率、老闆每天打電話問狀況的次數（T01 已設計）、異常發現時間。
6. 內部戰隊：用 Claude Code 雲端排程任務替 Y-001 做每日名單巡視（內部用，研究預覽可以接受）。

### 不做

- ❌ 不把客戶產品建在 Claude Duet 或雲端排程任務上（研究預覽、個人帳號、不支援台灣與 LINE）
- ❌ 不在 1 個工地通過之前就鋪開到 9 個工地，也不做多租戶平台
- ❌ 不讓 AI 在沒有人批准的情況下對外發訊息、叫料、付款
- ❌ 不把企業資料放進 `yes039/yes039`（公開 repo）或 GitHub Actions 的紀錄
- ❌ MVP 驗證之前，不採購 F03 提到的「25 萬 AI 硬體」。這個場景的 AI 費用每月只要幾百元，本機硬體要等「資料不能上雲」被證實是硬性要求才需要評估
- ❌ 不排 Claude Duet 候補（需要美國帳號）；等它開放 Team／Enterprise 或台灣地區時再評估

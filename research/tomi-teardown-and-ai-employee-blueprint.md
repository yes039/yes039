## 第二部分｜Tomi 本體到底是什麼？

| 選項 | 判斷 | 證據與推理 |
|---|---|---|
| **A. System Prompt** | 【高可信推測】**有，但不是單獨存在** | 任何有身份（Tomi）、有方法（T1）的 AI 都需要一段指令。但「裝進電腦」「都能裝」（T3、T8）表示它不是一段讓你貼進自訂指令的文字而已。它比較可能寫在 `SKILL.md`／`CLAUDE.md`／`AGENTS.md` 這類檔案裡 |
| **B. Claude Project** | 【低可信推測】 | Claude 免費版若沒有本機資料夾（P5），「記得你做到哪」可能要靠 Project 或聊天記錄。但沒有任何公開文字提到 Project |
| **C. Claude Skill** | 【高可信推測】 | ① Nora、Irene 都是「建在 Claude 裡」（N1、I1）；② Claude 免費版支援上傳 Skill ZIP（P1）；③ 「Claude 免費版」與「Codex」同時可裝（T8），最符合**同一份 `SKILL.md` 跨平台**的特性（P3）；④ 20 分鐘安裝＋文件（N5）符合「下載 ZIP → 上傳／放進資料夾」的工作量 |
| **D. Codex Skill／Agent** | 【高可信推測】 | T8 點名的是 **Codex**，不是「GPTs」或「自訂 GPT」。Codex 是在資料夾裡工作、會讀 `AGENTS.md` 的代理人（P4）。這指向**以資料夾為單位的檔案型封裝** |
| **E. Markdown＋Folder** | 【高可信推測】 | 「資料夾裡就多一份能用的東西」（T5）、「開專案」（T10）。產出是檔案、專案是資料夾 |
| **F. Prompt＋Workflow＋Templates** | 【高可信推測】 | 固定順序（T1）＝Workflow；固定產出種類「課綱、腳本、手冊、預售文案」（T4）＝需要 Templates 才能穩定產出 |
| **G. 有自己 Runtime 的 Agent（自架伺服器）** | 【低可信推測，接近排除】 | ① NT$810 終身使用（T7），自架伺服器有持續成本，商業上不合理；② 「裝進你電腦」「用你的 Claude／ChatGPT」；③ Nora 的自動化明說要靠 **Claude Pro**（N4），表示執行環境是平台的，不是作者的 |
| **H. 其他** | Custom GPT：【低可信推測】（文案說 Codex 不說 GPTs）；MCP Server：【低可信推測】（無證據，且對免費版使用者太難安裝）；純影片課程：【已排除】（T5、T8 明確是可安裝的東西） |

### 結論：如果把行銷包裝全部拿掉，Tomi 技術上是什麼？

> **【高可信推測】Tomi 是一包「檔案型的工作方法」：**
> 一組 Markdown 指令檔（身份＋方法＋步驟規則，很可能採 `SKILL.md`／`AGENTS.md` 格式）
> ＋ 產出範本（課綱、腳本、手冊、預售文案）
> ＋ 一套「專案資料夾」與「進度檔」的使用規則，
> 裝在使用者**自己的** Claude 或 Codex 裡，由平台的 LLM 執行。
>
> 它沒有自己的伺服器、沒有自己的模型、沒有自己的記憶系統。
> 它真正的「產品」是**藍諾把做課順序寫成 AI 能照做的規格**。

**信心提醒**：這是從宣稱和平台限制反推，沒有任何人公開過 Tomi 的檔案。買一份打開看，10 分鐘就能驗證或推翻。

## 第四部分｜Tomi 為什麼能續作？

### 先把兩件事分開

| | Memory（長期知道什麼） | State（這個工作做到哪） |
|---|---|---|
| 內容 | 你是誰、你的經驗、你的風格、你的偏好 | 目前在第幾階段、完成了哪些檔案、下一步是什麼、卡在哪 |
| 變動頻率 | 慢 | 每次工作都變 |
| 範例 | 「使用者是攝影師，教學風格直白」 | 「階段 3/6：驗證中；課綱 v2 已完成；待辦：訪談 3 位潛在學員」 |

### 可能的機制逐項評估

| 機制 | 能提供 Memory？ | 能提供 State？ | 對 Tomi 的可能性 | 理由 |
|---|---|---|---|---|
| Claude／ChatGPT 原生 Memory | 能（模糊的） | 很差（不精準、不可控） | 【低可信推測】作為主要機制 | 作者無法控制平台記憶的內容。宣稱「記得你做到哪」這麼具體，依賴平台記憶風險太高 |
| Claude Project | 能（專案知識） | 可以（若有進度檔放進去） | 【低可信推測】 | 無公開證據 |
| 聊天歷史 | 部分 | 部分 | 【低可信推測】 | 換一個新對話就沒了，不符合「下次回來」 |
| **專案資料夾中的檔案** | 能（例如「你的經驗訪談稿」本身就是 Memory） | **能**（進度檔） | **【高可信推測】主要機制** | ① 「資料夾裡就多一份」（T5）已經表示產出都是檔案；② 已產出的檔案本身就是進度的證據（有課綱檔 ＝ 課綱做完了）；③ 這是 Codex／Claude Code 社群最常見的續作做法（例如 `AI_CONTEXT.md`、`CLAUDE.md` 交接檔，見 [Threads 討論](https://www.threads.com/@chingshantu/post/DYbTMIYExGr/)） |
| 專用 state 檔（如 `progress.md`） | — | 能 | 【高可信推測】存在；**檔名【目前未知】** | 要讓 AI「一開口就知道做到哪」，最省 token、最可靠的方法是一份短的進度檔，開工先讀 |
| 工作摘要（每次結束時寫） | 能 | 能 | 【高可信推測】 | 和進度檔是同一件事的兩種寫法 |

### 結論

- **State**：【高可信推測】靠**專案資料夾裡的檔案**：一份進度檔，加上已產出的文件本身。開工規則大致是「先讀進度檔 → 告訴使用者做到哪 → 繼續」。
- **Memory**：**沒有任何證據顯示 Tomi 自建 Memory 系統。** 比較合理的解釋是：使用者在訪談階段講的經驗被寫成檔案（例如訪談紀錄），這些檔案之後被重複讀取，**效果上**就像記憶。這不是一個獨立的 Memory 系統，而是「檔案被重讀」。
- **Claude 免費版的疑點【目前未知】**：免費版沒有本機資料夾存取（Cowork 需 Pro，P5）。在免費版上，「資料夾」可能是：①在 Claude 的程式執行環境裡生成、讓使用者下載的檔案，下次再上傳；或 ② Project 知識庫。**這兩種方式都需要使用者手動搬檔案**，續作體驗可能明顯比 Codex 差。這是買一份就能驗證的關鍵點。

### Tomi 真正自己創造的價值在哪一層？

**全部在 Layer A，而且集中在其中兩件事：**

1. **方法論**：「先訪談、再定位、驗證、製作、上架」這個順序，以及每一步要問什麼、做到什麼程度才算完成。這是藍諾「帶上萬名學員」累積出來的（T1），是別人抄不走的部分。
2. **把方法論翻譯成 AI 可執行的規格**：範本、完成條件、驗收點、續作規則。

其他全部是借來的：LLM 是平台的，檔案能力是平台的，自動化是平台付費功能（N4 明講要 Pro），內容原料是使用者的。

**對我們的意義：** 做一個 Tomi，工程量很小；真正的門檻是**你有沒有一套被驗證過、可以寫成步驟的產業方法**。

## 第七部分｜Tomi 解剖圖

### 你原本的圖哪裡要改

你的原圖是一條直線：使用者 → Identity → … → Human Gate → State Update → 下一次續作。依研究結果，有 4 處要修正：

1. **起點不是 Identity，是「讀 State」。** 續作能成立，是因為每次開工**先讀進度檔**，再決定這次做什麼。
2. **Human Gate 不在最後，在每個階段之間。** 「你只要驗收像不像你」（T4）表示每份產出都要被驗收，驗收通過才推進階段。
3. **Skills 不在平台能力「之上」。** Skills 是寫給平台執行的檔案；兩者是「規格」和「執行者」的關係，不是上下層。
4. **Memory 和 State 要分開畫。** Memory 是被反覆讀取的使用者資料檔；State 是每次都被改寫的進度檔。

### 修正後的解剖圖

```
                    ┌──────────────────────────────────────────┐
                    │     Layer A：Tomi 安裝包（作者提供）       │
                    │  Identity ─ Mission ─ Method（階段定義）   │
                    │  Skills（各階段步驟）─ Templates ─ 規則    │
                    └───────────────────┬──────────────────────┘
                                        │ 被平台載入
  ┌──────────────┐    ┌─────────────────▼──────────────────────┐
  │   使用者      │───▶│  Layer B：Claude / Codex 平台（執行者）  │
  │  「Tomi，繼續」│    │  LLM ＋ 檔案讀寫 ＋（Pro）排程/連接器    │
  └──────▲───────┘    └─────────────────┬──────────────────────┘
         │                              │
         │                 ① 開工：讀 State（做到哪）
         │                 ② 讀 Memory 檔（你是誰、你的經驗）
         │                 ③ 依 Method 決定本階段任務
         │                              │
         │                 ④ 工作：訪談／起草（呼叫對應 Skill＋Template）
         │                              │
         │                 ⑤ 產出 Artifact → 寫入專案資料夾
         │                              │
         └──── ⑥ Human Gate：你驗收「像不像你」────┐
                     │ 不通過 → 回到 ④ 修改          │
                     │ 通過 ↓                        │
                  ⑦ 更新 State（階段推進、下一步）     │
                  ⑧ 必要時更新 Memory 檔（新學到的偏好）│
                     │                                 │
                  ⑨ 收工 ─── 下次從 ① 開始 ◀──────────┘

  ┌──────────────────────────────────────────────────────────┐
  │  Layer C：專案資料夾（使用者的）                           │
  │  Memory 檔：訪談紀錄、你的經驗、你的語氣                    │
  │  State 檔：目前階段、已完成、下一步、卡點                   │
  │  Artifacts：課綱、腳本、手冊、預售文案                      │
  └──────────────────────────────────────────────────────────┘
```

整張圖的結構是【高可信推測】；每個方框的**具體檔名與格式**是【目前未知】。

## 第八部分｜我們的「Tomi 1、2、3…」：產業 × AI 身份

### 選擇標準（依 Tomi 的研究結果反推）

Tomi 能成立，是因為它符合 5 個條件。我們用同樣 5 個條件篩選：

1. **有一套可以寫成步驟的方法**（Tomi 的 Method）
2. **輸入資料取得容易**：不需要 API，老闆能匯出 CSV、截圖、貼文字就行
3. **有固定節奏**：每天／每週都要做，才會天天打開、天天產生 State
4. **產出可以被驗收**：老闆一看就知道對不對
5. **決策權清楚**：AI 做分析與起草，人批准對外動作，法規風險低

## 第九部分｜「AI 專業員工母版」

### 核心發現

把 Tomi 和上面 7 個候選放在一起比，**大約 70% 的結構完全相同**。不同的只有三種東西：產業知識、職位職責、每家公司自己的資料。

### 四層結構

| 元素 | 母版（共同骨架） | 產業包 | 職位包 | 公司初始化 |
|---|---|---|---|---|
| **Identity** | 格式、語氣規則、「員工」行為準則 | — | 名字、職稱、個性 | 老闆怎麼稱呼它 |
| **Mission** | 格式 | — | ✅ 這個職位要達成什麼 | 本店今年目標 |
| **Industry Knowledge** | 知識檔的格式 | ✅ 名詞、KPI 定義、行業基準、法規 | — | — |
| **Method** | 階段式工作法的格式（階段、完成條件、驗收點） | ✅ 行業的標準做法 | ✅ 這個職位的日／週／月節奏 | — |
| **Skills** | 共用技能：讀表格、算數字、寫報告、追蹤待辦、比較上週 | ✅ 行業專用分析（例如菜單工程） | ✅ 職位專用產出（例如家長溝通） | — |
| **Tools** | 平台檔案讀寫、程式執行、排程的使用規則 | 常見系統的**欄位對照表**（例如各家 POS） | — | ✅ 這家店用哪個 POS、怎麼匯出 |
| **Workspace** | ✅ 標準資料夾結構 | — | — | ✅ 建立資料夾 |
| **Memory** | ✅ Memory 檔格式與更新規則 | — | — | ✅ 店家設定、老闆偏好 |
| **State** | ✅ State 檔格式、開工讀／收工寫的規則 | — | — | 從零開始 |
| **Workflow** | ✅ 開工 → 工作 → 產出 → 驗收 → 更新 State → 收工 | — | ✅ 每日／每週固定流程 | — |
| **Artifact Contract** | ✅ 每份產出的共同規格（標題、日期、資料來源、結論、待批准事項） | ✅ 行業版範本 | ✅ 職位版範本 | 老闆偏好的格式微調 |
| **Human Gate** | ✅ 「對外、花錢、改價、改人」一律要批准的底線 | ✅ 行業法規紅線 | ✅ 職位的決策權限 | 老闆可以再收緊 |
| **Outcome** | ✅ 量測格式 | ✅ 行業 KPI | ✅ 職位 KPI | ✅ 本店基準值 |
| **Install** | ✅ 安裝包結構、安裝教學 | — | — | — |
| **Initialization** | ✅ 初始化訪談流程 | ✅ 產業題庫 | ✅ 職位題庫 | ✅ 回答問題 |
| **Update** | ✅ 版本號、升級時**不覆蓋** Memory／State／Artifacts | 產業包可獨立更新 | 職位包可獨立更新 | — |

### 答案：能不能做到這個公式？

> **一套 AI 員工母體 ＋ 產業包 ＋ 身份包 ＋ 客戶自己的企業資料 ＝ 一名可以直接上工的 AI 專業員工**

**能，而且技術上不難。** 現在的 Skill 資料夾格式（`SKILL.md`＋資源檔，P2、P3）本來就支援「一個資料夾裝一包能力」，Claude 和 Codex 都能讀。母版、產業包、職位包可以是三組獨立的資料夾。

**真正的難點不在技術，而在三件事：**
1. **產業包的品質**：需要真正懂行的人寫方法（這就是藍諾的 Layer A 價值）。
2. **初始化的體驗**：老闆願不願意花 30 分鐘回答問題、匯出報表。
3. **資料進來的摩擦**：每天要有人把 POS 報表丟進資料夾。這一步沒解決，AI 員工就會「閒置」。

## 第十部分｜MVP：「AI 店長 × 餐飲業」完整閉環

### 平台選擇

| 選項 | 續作能力 | 自動化 | 使用者門檻 | 建議 |
|---|---|---|---|---|
| Claude 免費版（網頁） | 弱（檔案要手動上下傳） | 無 | 低 | 不作為 MVP 主線 |
| **Claude Pro＋Cowork（桌面版）** | **強（直接讀寫本機資料夾）** | 有（排程） | 中 | **MVP 主線 A** |
| **ChatGPT＋Codex app** | **強（本機資料夾）** | 有（限額內） | 中 | **MVP 主線 B** |

**建議：MVP 先只做一個平台**（Claude Cowork 或 Codex 擇一），但指令檔用跨平台格式（`SKILL.md`＋同內容的 `CLAUDE.md`／`AGENTS.md`），之後再擴。

### 安裝包結構

```
ai-store-manager/
├── CLAUDE.md / AGENTS.md        ← 身份＋開工/收工規則（兩份內容相同）
├── skills/
│   ├── onboarding/SKILL.md      ← 初始化訪談
│   ├── daily-report/SKILL.md    ← 每日戰報
│   ├── anomaly-check/SKILL.md   ← 異常偵測
│   ├── cost-review/SKILL.md     ← 食材成本與毛利
│   └── weekly-review/SKILL.md   ← 週報與改善追蹤
├── templates/
│   ├── daily-report.md          ← 戰報固定格式
│   └── weekly-review.md
├── knowledge/
│   ├── restaurant-kpis.md       ← 產業包：KPI 定義與基準
│   └── pos-mappings.md          ← 常見 POS 匯出欄位對照
├── store/                       ← 公司初始化後才有內容
│   ├── profile.md               ← Memory：店家基本資料、目標、老闆偏好
│   ├── menu-costs.csv
│   └── staff.md
├── inbox/                       ← 老闆每天把 POS 報表丟這裡
├── reports/daily/  reports/weekly/
└── state/
    ├── STATE.md                 ← 做到哪
    └── actions.md               ← 改善事項追蹤表
```

### 閉環：7 個步驟

| 步驟 | 發生什麼 | 產生／改變的檔案 |
|---|---|---|
| **1. 安裝**（約 15 分鐘） | 下載資料夾 → 用 Cowork／Codex 開啟 → 說「店長，報到」 | — |
| **2. 初始化**（約 30 分鐘） | 店長訪談老闆：店型、營業時間、目前的痛、目標食材成本率、用哪個 POS、怎麼匯出；老闆上傳菜單與成本 | `store/profile.md`、`menu-costs.csv`、`staff.md`；`STATE.md` 寫入「已初始化，等待第一份資料」 |
| **3. 第一天上工** | 老闆把昨天的 POS 報表丟進 `inbox/`，說「今天的戰報」 | 店長**先讀 `STATE.md`** → 讀 `profile.md` → 讀報表 → 依 `pos-mappings.md` 對欄位 → 計算 |
| **4. 交件** | 產出一頁戰報：昨日營收與上週同日比、前 3 名與後 3 名品項、異常（例如某品項銷量暴跌、某時段人效過低）、**今天只做一件事**的建議 | `reports/daily/2026-09-25.md` |
| **5. Human Gate** | 老闆看完回覆：同意／不同意／修改建議。店長**不會**自己改價、改班表 | 老闆同意的建議寫入 `actions.md`（負責人、到期日） |
| **6. 保存 State** | 收工前店長更新 `STATE.md`：資料收到哪天、本週重點、待追蹤事項、下一步 | `STATE.md`；如果老闆表達新偏好（「報告不要超過一頁」），寫入 `profile.md` |
| **7. 第二天續作** | 老闆開啟資料夾，說「早安」。店長讀 `STATE.md` 後主動回報：「昨天同意的『週三備料減少 20%』今天到期，執行了嗎？今天的報表還沒收到。」 | 循環回到步驟 3 |

### `STATE.md` 最小格式

```markdown
# 店長工作狀態
- 最後更新：2026-09-25 22:10
- 資料已收到：至 2026-09-24
- 本週重點：週三晚餐時段人效偏低
- 下一步：等待 9/25 POS 報表
## 待追蹤（詳見 actions.md）
- [ ] A-003 週三備料減少 20%｜老闆｜9/26 到期
## 卡點
- 外送平台報表尚未提供
```

### 開工與收工規則（寫在 `CLAUDE.md`／`AGENTS.md`）

```
開工：
1. 讀 state/STATE.md 與 state/actions.md
2. 讀 store/profile.md
3. 先用兩句話回報：做到哪、今天有什麼到期
4. 檢查 inbox/ 有沒有新資料

收工（每次交件後）：
1. 更新 STATE.md（不要刪除歷史，只改目前狀態）
2. 老闆同意的建議寫入 actions.md
3. 老闆新說的偏好寫入 profile.md

絕對不做：
- 對外發布、改價、改菜單、改班表、下單
- 以上一律只能寫成「待批准建議」
```

### MVP 成功標準

- 老闆連續 2 週、每週至少 5 天有打開並交出報表
- 至少 3 條改善事項被執行並追蹤到結果
- 老闆能說出「它幫我發現了什麼我原本沒注意的事」

## 第十一部分｜能借不造：哪些借、哪些自己造

### 直接借（不要自己開發）

| 能力 | 借誰 |
|---|---|
| 語言模型、推理、寫作 | Claude／OpenAI |
| 檔案讀寫、本機資料夾 | Claude Cowork／Claude Code／Codex app |
| 計算（成本、毛利、人效） | 平台的程式執行 |
| Skill 載入格式 | `SKILL.md` 開放格式 |
| 排程（每天自動跑） | 平台的排程功能（Pro 以上；各平台可用性以官方文件為準） |
| 外部連接（Google Drive、Meta） | 平台連接器 |
| 付款、會員、交付 | 現有課程平台或電商平台 |

### 值得自己造（這才是產品）

| 項目 | 為什麼值得 |
|---|---|
| **產業方法論**（產業包） | 唯一的護城河。Tomi 的價值就在這裡 |
| **Artifact 規格**（每份報告長什麼樣） | 決定老闆會不會每天打開 |
| **State／Memory 檔規格與開工收工規則** | 決定「續作」體驗；母版的核心 |
| **初始化訪談** | 決定 30 分鐘內能不能上工 |
| **POS／系統欄位對照表** | 降低「資料進來」的摩擦；累積越多越難被抄 |
| **Human Gate 規則** | 決定老闆敢不敢用 |
| **測試案例**（用真實報表驗證產出品質） | 沒有這個，每次更新都可能讓店長變笨 |
| **安裝體驗**（影片、文件、客服） | Nora 用 20 分鐘安裝影片當賣點（N5），這是轉換率的關鍵 |

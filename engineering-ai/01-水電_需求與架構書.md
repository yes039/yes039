# 01｜水電企業 AI 系統需求與架構書

產品暫名：《八工地 AI 經營指揮台》
狀態：需求研究階段規劃稿 v1.0｜未建置、未取得企業授權、未接觸真實資料

標記法：**【事實】** 已知　**【待訪談】** 要問老闆　**【假設】** 待驗證，驗證前不得當成結論

---

## 一、需求原因

| 類型 | 內容 |
|---|---|
| 【事實】 | 同時管理 8 個工地 |
| 【事實】 | 日常靠 LINE 群組與電話溝通 |
| 【事實】 | 目標：降低資訊分散與管理負擔 |
| 【待訪談】 | 員工人數、自有師傅與外包比例、工程類型（新建／裝修／公共工程／廠房）、派工方式、材料怎麼叫、誰管帳、請款流程 |
| 【假設 H1】 | 老闆每天花大量時間「打電話問狀況」，且仍常在事後才知道問題 |
| 【假設 H2】 | 資訊散在多個 LINE 群，重要訊息被洗掉，事後找不到「誰說過什麼」 |
| 【假設 H3】 | 缺料、叫錯料、重複叫料造成停工或浪費 |
| 【假設 H4】 | 工作口頭交辦，沒有完成確認，責任不清 |
| 【假設 H5】 | 現場師傅願意每天花 1–2 分鐘用手機回報（**這是全案最大風險**） |

為什麼需要 AI，而不只是需要一張表：
- 師傅不會填表，但會傳 LINE、拍照、講語音 → **AI 的第一個工作是把隨手訊息轉成結構化紀錄**。
- 八個工地每天的訊息量，老闆讀不完 → **AI 的第二個工作是篩出「今天要老闆決定的事」**。
- 表格不會自己追人 → **系統的第三個工作是找出誰沒回報、哪件事過期**（這件是規則，不需要 AI）。

## 二、解決痛點

| # | 痛點 | 現有流程（推測，待訪談確認） | 問題原因 | AI 能承擔 | 必須人工判斷 | 預期改善方式 |
|---|---|---|---|---|---|---|
| P1 | 資訊分散 | 每工地一個 LINE 群＋私訊＋電話 | 沒有單一紀錄處；電話不留痕 | 把回報訊息、照片、語音轉成「工地／日期／類型／內容」結構化紀錄，並保留原文 | 確認 AI 理解是否正確（回傳確認卡一鍵修正） | 每則紀錄可回溯到原訊息；老闆只看一頁 |
| P2 | 異常發現太晚 | 師傅打電話給老闆或主任才知道 | 沒有主動回報機制；小事拖成大事 | 從回報內容辨識異常（停工、缺料、業主變更、安全、品質）並分級建議 | 異常等級最後由主任／老闆確認；處理方式由人決定 | 異常有編號、負責人、期限、狀態，逾期自動標紅 |
| P3 | 派工責任不清 | 老闆或主任口頭／LINE 交辦 | 交辦沒有完成確認 | 從對話擷取「誰、做什麼、何時前」產生待辦草稿 | 派誰去哪由老闆／主任決定 | 每件交辦有接收、完成、照片佐證三個狀態 |
| P4 | 缺料停工 | 師傅打給主任，主任打給材料行 | 叫料不留紀錄；沒人知道誰已經叫了 | 從回報擷取料名、規格、數量、需要日；比對是否已有相同待辦避免重複 | 規格是否正確、向誰買、價格由人確認 | 缺料單有狀態：提出 → 已叫料 → 已到場 |
| P5 | 老闆被電話綁住 | 每天打一輪電話問進度 | 沒有彙整資訊 | 每日 18:00 產出管理摘要：要決定的事、異常、未回報、明日重點 | 老闆決定優先順序 | 老闆改成「看摘要 → 只打必要的電話」 |
| P6（第二階段） | 零星追加收不到錢 | 業主現場口頭要求加做 | 沒有書面紀錄與業主確認 | 擷取追加項目、照片、估計工時料 | 報價與是否收費由老闆決定 | 追加單留存業主確認，列入請款 |

## 三、配置規模

| 項目 | MVP 輕量驗證版 | 標準營運版 | 完整企業版 |
|---|---|---|---|
| 目的 | 驗證「師傅會回報、老闆會看摘要」 | 8 工地日常營運 | 串接財務、請款、成本 |
| 工地數 | **2** | 8 | 8＋歷史工程 |
| 使用者 | 老闆 1、主任 1–2、師傅 4–10、行政 0–1 | 老闆、主任、師傅、行政、材料採購 約 15–40 人 | 再加會計、外包班長 |
| 權限 | 3 種：老闆（全部）、主任（所屬工地）、師傅（只能回報與看自己的待辦） | 5 種：再加行政、採購 | 再加會計、外包（限定工地與欄位）、稽核唯讀 |
| 資料庫 | 單一雲端資料庫（建議 Cloudflare D1）：工地、人員、回報、異常、待辦、缺料、摘要、稽核紀錄 | 同左＋派工排程、料件主檔、廠商主檔 | 同左＋合約、追加單、請款、成本科目；需備份與保存政策 |
| AI 模組 | ① 訊息結構化（文字／照片／語音轉文字）② 異常分級建議 ③ 每日摘要 | 再加 ④ 重複缺料比對 ⑤ 週報與工地比較 ⑥ 待辦擷取 | 再加 ⑦ 追加單草稿 ⑧ 成本異常提示 ⑨ 自然語言問答（「上週 A 案用了多少 PVC 管？」） |
| 入口 | LINE 官方帳號一對一聊天＋圖文選單＋LIFF 表單；老闆手機網頁 | 同左＋電腦版八工地總覽 | 同左＋行政後台、匯出 Excel |
| 技術架構 | Cloudflare Workers（沿用 FB 工作室 V5 底座）＋D1＋R2（照片）＋LINE Messaging API＋Claude API | 同左，加排程任務與通知 | 同左，加會計系統匯出／匯入介面 |
| 成本構成（詳見 07） | 開發人日；雲端多半在免費額度；AI 約每月 US$5 以內（估算）；LINE 推播額度可能需付費方案 | 雲端＋LINE＋AI 估每月 NT$2,000–6,000；維護時數 | 再加整合開發、資料保存、維護合約 |
| 維護需求 | 每週檢查回報率與 AI 誤判，調整提示詞 | 每月一次欄位／字典調整；LINE 權杖、雲端金鑰輪替 | 定期備份演練、權限稽核、版本升級 |

## 四、操作用法

### 輸入原則
- **師傅只用 LINE**，加入公司 LINE 官方帳號（一對一聊天）。不要求下載 App、不要求記帳號密碼。
- 圖文選單 4 顆鍵：`📋 今日回報`　`⚠️ 異常`　`📦 缺料`　`✅ 完成交辦`。
- 也可以直接傳文字、照片、語音；AI 整理後**回一張確認卡**：「我理解為：A 工地／3F 給水管完成 70%／缺 1/2 吋彎頭 20 個，明早要。　[正確]　[修改]」。按「正確」才寫入正式紀錄；按「修改」直接改欄位。
- 不讀既有群組歷史訊息、不聽電話。電話內容若重要，由接電話的人事後用「語音備忘」補一筆。

### 每日情境

| 時間 | 角色 | 動作 | 系統回應 |
|---|---|---|---|
| 07:30 | 主任 | 在 LINE 按「今日回報」→ 選工地 → 確認今日出工名單（預設帶昨日名單） | 記錄出工；未設定出工的工地標「未開工或未回報」 |
| 白天 | 師傅 | 遇到問題按「異常」或直接拍照＋語音 | 確認卡 → 寫入異常，通知該工地主任；高等級同時通知老闆 |
| 白天 | 師傅 | 按「缺料」講「1/2 吋彎頭 20 個明早要」 | 確認卡 → 缺料待辦；若同工地 3 天內有同料待辦，提示「可能重複」 |
| 白天 | 老闆／主任 | 在 LINE 或網頁交辦：「小陳明天去 B 案補漏水」 | 產生交辦，小陳收到通知需按「收到」 |
| 16:30 | 系統 | 檢查未回報工地 | 只提醒該工地主任一次（避免洗版） |
| 17:30 | 師傅／主任 | 按「今日回報」：完成什麼、進度 %、明日計畫、照片 1–3 張 | 確認卡 → 寫入 |
| 18:00 | 系統 | 產生每日摘要 | 推給老闆（LINE 一則＋網頁連結） |
| 18:00–21:00 | 老闆 | 手機看首頁：先看「要你決定」→ 異常 → 未回報 | 每一條可點開看原始訊息與照片；可指派、改等級、標記已處理 |
| 隔日 | 行政 | 電腦版看缺料待辦，叫料後改「已叫料」，到場改「已到場」 | 狀態變更寫入稽核紀錄 |
| 每週 | 管理者 | 看回報率、AI 被修正率、逾期異常數 | 決定要不要調整欄位或提醒方式 |

## 五、預期效果（KPI 與停損）

> 以下都是**待量測**的指標。導入前先量基準，沒量基準就不宣稱改善。

| KPI | 定義 | 基準怎麼量（導入前 5 個工作日） | 驗證目標（假設值，需老闆同意） |
|---|---|---|---|
| K1 回報率 | 應回報工地日中有完成「今日回報」的比例 | 導入前為 0（沒有正式回報），改量「老闆每天要打幾通電話才知道全部工地狀況」 | 2 週內 ≥ 80% |
| K2 老闆追問電話數 | 老闆為了了解進度主動撥出的電話數／日 | 老闆用紙或手機通話紀錄記 5 天 | 下降（幅度不預設） |
| K3 異常發現時間 | 異常發生到老闆或主任知道的時間 | 訪談回溯近 1 個月 3–5 件事件 | 有紀錄可量即可，30 天後比較 |
| K4 異常逾期率 | 超過期限仍未結案的異常比例 | 導入前無資料 | 30 天內建立數據，再訂目標 |
| K5 AI 理解正確率 | 確認卡被直接按「正確」的比例 | 導入後第 1 週量 | ≥ 85%，低於 70% 要改提示詞或改表單 |
| K6 摘要有用度 | 老闆每日對摘要按「有用／沒用」 | 導入後量 | 連續 2 週「有用」≥ 70% |
| K7 缺料重複／臨時叫料 | 同料重複叫或當天急叫次數 | 行政回溯近 1 個月 | 30 天後比較 |

**停損條件（任一成立就停，不擴大到 8 工地）**
1. 第 2 週結束時 K1 回報率 < 50%，且改提醒方式後第 3 週仍 < 50%。
2. 老闆連續 5 個工作日沒有打開摘要。
3. K5 < 70% 且兩次修正後仍未改善。
4. 主任反映回報負擔「比打電話還麻煩」且多數師傅同意。

## 六、系統架構

```
 師傅／主任手機（LINE）            老闆手機（網頁）      行政／管理者電腦（網頁）
        │ 文字／照片／語音                 ▲                     ▲
        ▼                                 │                     │
 LINE 官方帳號 ──Webhook──► 收件層（原始訊息永久保存：raw_messages）
                                │
                                ▼
                    AI 結構化（Claude Haiku 級）
                    輸出＝欄位＋每欄來源（訊息 ID／照片 ID）＋信心
                                │
                                ▼
                     確認卡回 LINE ──► [正確] / [修改]
                                │
                                ▼
       正式紀錄：daily_reports / issues / tasks / material_requests
                                │（每次異動寫 audit_log）
                ┌───────────────┼────────────────┐
                ▼               ▼                ▼
        規則引擎：未回報     AI 每日摘要        儀表板 API
        逾期、重複缺料      （Claude Sonnet 級）  （手機首頁、八工地總覽）
```

### 三項必備機制
1. **資訊來源追溯**：每一筆正式紀錄都存 `source_message_ids`；摘要的每一句都帶紀錄 ID，點開可看到原訊息、照片、誰在何時說的。AI 產出沒有來源的句子，一律不顯示。
2. **人工更正**：任何欄位可改；改了保留舊值、改的人、時間、原因（`audit_log`），欄位標記 `source = ai | human | rule`（沿用玉欣珍小購的 `model／dictionary／human` 做法）。人工改過的值，AI 不得覆寫。
3. **未回報標記**：規則判斷，不靠 AI。工地在「施工中」狀態且當日 17:30 前無回報 → 標 `未回報`（灰底）；連續 2 日 → 列入老闆摘要；主任可標「今日停工（原因）」解除。

### LINE 限制與替代（不假裝自動化）

| 限制 | 對策 |
|---|---|
| Bot 讀不到加入前的歷史訊息 | 不做歷史匯入；必要的舊資料由行政一次性整理成工地清單 |
| 群組中 Bot 只能收到加入後的訊息，且全員訊息都會被收進來，有隱私疑慮 | MVP **不放進群組**，只用一對一聊天；既有群組照常聊天 |
| 電話內容讀不到 | 「語音備忘」按鍵，講完由 AI 轉文字＋確認卡 |
| 主動推播有則數額度 | 只推「老闆摘要」與「主任未回報提醒」；其他用回覆訊息（不計推播額度，需依官方當期規則查證） |
| 師傅換手機或離職 | 人員主檔停用即可；LINE 綁定以邀請碼＋主任核可建立 |

## 給兩位老闆的一頁說明

| | 水電（八工地） | 營造 |
|---|---|---|
| **為什麼需要 AI** | 八個工地的訊息散在 LINE 和電話，老闆靠一通通電話拼湊狀況 | 文件多（標單、日報、會議、估驗）、人手少；想知道 AI 能不能幫忙，以及該不該買硬體 |
| **能解決什麼** | 師傅隨手傳的文字、照片、語音，自動整理成工地紀錄；誰沒回報、哪件事逾期一眼看到；每晚一頁摘要 | 招標文件重點與工項自動整理；日報與會議紀錄草稿；發包估驗到期與差異提醒；多工程一頁總覽 |
| **需要配置多少** | 先 2 個工地；不買硬體；用現有手機與 LINE；AI 費用估每月約 NT$100–200 | 先用雲端試 30 天、不買硬體；以假設用量估算，25 萬主機約要 7 年才抵得過雲端 AI 費用 |
| **每天怎麼操作** | 師傅下班前 LINE 回報 1 分鐘並按「正確」；老闆晚上看手機一頁、點開有疑問的項目 | 主任下班前語音＋照片產日報草稿；工務上傳標單取得整理結果；老闆早上看總覽、核准待決事項 |
| **預期效果（待實測）** | 回報率、追問電話數、異常發現時間、缺料重複次數：導入前先量基準，30 天後如實比較 | 標單整理時間與擷取準確率、日報準時率：30 天實測後再決定是否擴大與投資 |

## 獨立技術判斷

1. **水電案的最大風險不在技術，在回報意願。** LINE 收訊、AI 整理、摘要都是成熟技術，AI 費用很低（估每月 NT$100–200）。真正的未知是「師傅會不會每天回報」。所以第一步是**不寫程式、用 LINE 文字範本試跑 3 天**，回報率 ≥ 60% 再開發。
2. **不要把 Bot 放進既有 LINE 群組。** Bot 讀不到加入前的歷史訊息；放進群組會收到業主、廠商的對話，有隱私問題，也會被閒聊淹沒。改用**官方帳號一對一＋確認卡**，資料品質較好，也能追溯。
3. **未回報、逾期、燈號用規則判斷，不用 AI。** AI 只負責「把話整理成欄位」和「寫摘要」，而且每句都要帶來源。這樣錯了能追，老闆也信得過。
4. **營造案目前沒有買 25 萬硬體的理由。** 在假設用量下，三年 TCO：雲端約 NT$4–23 萬，本地約 NT$38–68 萬（皆不含軟體開發）。而且買了硬體仍然沒有系統。本地部署只在三種情況值得重新評估：合約要求資料不得上雲、實測用量遠高於假設、本地模型實測準確度可接受。**先拿規格、先用去識別化文件做雲端實測。**
5. **營造案的第一個驗證是「文件擷取準確度」，不是系統。** 標單工項召回率與數量正確率若達不到門檻，就代表仍需人工全核，整個價值主張要重新評估；這可以用 3 份舊文件、幾乎零成本先驗證。
6. **共用母版以「水電 MVP」為第一個實作驗證。** 不先抽象出完整平台；先用水電把核心（工地、人員、回報、異常、任務、摘要、稽核、欄位來源）做實，營造只新增產業模組。驗收時記錄「哪些靠設定、哪些要改程式」，作為母版 V1.1 的依據。
7. **既有資產沿用三塊，不搬餐飲邏輯**：FB 工作室 V5 的雲端底座與測試紀律、玉欣珍小購的「拍照 → AI 辨識 → 人工確認」狀態機與欄位來源標記、海豹小隊的人工節點方法論。玉欣珍儀表板本體、90 天 KPI、Airtable 商機交接本輪**未找到**，不列入可沿用清單。

## 最值得先驗證的 MVP

**水電《八工地 AI 經營指揮台》2 工地版，聚焦一條價值鏈：**

> **師傅 LINE 回報 → AI 整理＋確認卡 → 未回報自動標記 → 18:00 老闆一頁摘要（每句可追溯）**

- 先做這條，是因為它同時驗證最大風險（回報意願）與最核心價值（老闆少打電話）。
- 異常追蹤、缺料待辦、交辦責任在同一份資料上依序加上（06 階段 2 第 6–8 項）。
- 營造案在此期間只做：訪談、索取硬體規格、3 份文件的雲端擷取實測。

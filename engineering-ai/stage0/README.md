# 階段 0｜企業需求訪談工具包（G-002-ORDER-002）

執行原則：**先了解需求，再設計方案；先驗證痛點，再決定開發。**
本階段不開發、不部署、不採購、不接入客戶正式系統。未經 Shen 核准，不進入系統開發。

## 交付

| 編號 | 文件 | 用途 | 誰填 |
|---|---|---|---|
| F01 | [企業基本資料與經營現況問卷](F01-企業基本資料與經營現況問卷.md) | 兩產業共用；訪談前先發或訪談時填 | 老闆／行政 |
| F02 | [企業管理痛點與損失評估表](F02-企業管理痛點與損失評估表.md) | 把「很困擾」變成有案例、有頻率、有金額的痛點 | 訪談者＋老闆 |
| F03 | [水電／營造專屬深度訪談表](F03-水電營造專屬深度訪談表.md) | 分產業深挖流程；含主任、師傅、行政訪談 | 訪談者 |
| F04 | [AI 導入需求診斷報告母版](F04-AI導入需求診斷報告母版.md) | 含「需求卡」標準格式：訪談結果 → AI 系統需求 | 訪談者撰寫、Shen 審核 |
| F05 | [需求優先級與 MVP 建議表](F05-需求優先級與MVP建議表.md) | 評分、排序、選出前三大問題與 MVP | 訪談者撰寫、Shen 核准 |
| T01 | [水電 3 天人工回報試跑計畫](T01-水電3天人工回報試跑計畫.md) | 不寫程式，驗證師傅會不會回報 | 訪談者＋主任 |

## 使用順序

```
訪談前    F01 先發給老闆（或訪談時當場填）
訪談 1    老闆：F01 補問 → F02 痛點盤點（約 60–90 分）
訪談 2    第一線：F03 主任、師傅／工務、行政（各 20–30 分，可到工地）
          水電：同時啟動 T01 三天試跑
訪談後    每個痛點寫成 F04 需求卡 → F05 評分排序
交付      F04 診斷報告（前三大問題、量化價值、MVP、不適合 AI 的項目、下一階段範圍成本風險）
          → Shen 核准 → 才能進入開發
```

## 資訊確認狀態（全部表單共用）

| 標記 | 意義 | 能否寫進診斷結論 |
|---|---|---|
| ✅ 已確認 | 有文件、紀錄、照片或現場觀察佐證（填寫證據位置） | 可以 |
| 🗣 口述 | 受訪者說的，尚無佐證 | 可以寫，但必須標「口述」，且需附基準量測方式 |
| ❓ 待確認 | 沒問到、對方不知道、或我們推測的 | **不得**當成企業現況；預設值一律是「❓ 待確認」 |

## 資料處理規則（強制）

1. **本 repo 是公開的，只放空白模板。** 填過的問卷、訪談紀錄、錄音、照片、試跑資料**一律不得 commit**。
2. 填寫後存放於 Shen 指定的**私人位置**（建議：Google Drive 私人資料夾「C-001 訪談資料」，僅 Shen 與訪談者有權限）。
3. 企業以代號表示：水電＝`EP-01`、營造＝`EC-01`；工地以 `A`、`B`…表示；人員以角色表示（老闆、主任 1、師傅 2）。真實名稱只出現在私人位置的「代號對照表」。
4. 錄音前取得受訪者口頭同意並記錄在 F01 第 J 節；試跑前取得書面同意。
5. 若要將客戶資料交給 AI 工具整理（例如人工產生試跑摘要），需在同意書中明列，且只用去識別化內容。
6. 本資料夾的 `.gitignore` 已排除 `filled/`、`訪談紀錄/`、`*_已填*`、`*.filled.*`、錄音與試跑資料，防止誤傳；**仍以人工確認為準**。

## 與 C-001 的關係

C-001 的 `09-待老闆確認的訪談問題清單.md` 已由本工具包取代（題目已併入 F01–F03 並補上案例、頻率、損失欄位）。C-001 的架構與 MVP 方向僅作「待驗證假設」，訪談結果與之不符時以訪談結果為準。

## 2. 三套系統工時估算依據

### 2.1 估算方法
1. **工作分解（WBS）**：把每套系統拆成畫面與功能單元，逐項以「純手寫工時」估計（依一般 Next.js + Postgres 專案的經驗值）。
2. **AI 加速係數**：依工作性質套用不同係數，而不是整體打折：

| 工作性質 | 例子 | AI 輔助後工時 / 純手寫 | 理由 |
|---|---|---|---|
| 樣板型 | CRUD 表單、列表、後台頁面 | 0.3–0.4 | Claude Code 產生速度最快，人主要做檢查 |
| 邏輯型 | 時段計算、點數規則、狀態流轉 | 0.5–0.6 | 需反覆釐清規則與邊界情況 |
| 整合型 | LINE 登入、推播、金流 Webhook | 0.7–0.9 | 時間花在申請設定、讀文件、實機測試、等待審核，AI 幫不上 |
| 驗證型 | 手機實機測試、資安測試、修 bug | 0.7–0.8 | 必須人工操作與判斷 |

3. **區間表達**：下限 = 規格清楚、無意外；上限 = 遇到一次中型卡關（例如 LINE 登入橋接需改方案）。

### 2.2 預約系統 WBS（範例，最完整）

| 工作單元 | 性質 | 純手寫 (h) | AI 輔助 (h) |
|---|---|---|---|
| 資料表設計與 migration（服務、人員、營業時間、預約） | 樣板 | 6–8 | 2–3 |
| 店家設定頁（服務、人員、營業時間、休假） | 樣板 | 14–18 | 5–7 |
| 時段計算（營業時間 − 休假 − 已預約 − 緩衝） | 邏輯 | 10–14 | 5–8 |
| 防重複預約（資料庫排他約束）+ 並發測試 | 邏輯 | 6–10 | 3–6 |
| 顧客預約流程（選服務→人員→時段→確認） | 樣板 | 12–16 | 4–6 |
| 我的預約（取消、改期規則） | 邏輯 | 8–10 | 4–5 |
| 後台日／週行事曆、手動新增、到店／爽約 | 樣板 | 14–20 | 5–8 |
| LINE 通知（成功、提醒、取消）+ 排程 | 整合 | 8–12 | 6–9 |
| 手機實機測試、修正 | 驗證 | 10–16 | 7–11 |
| **合計** | | **88–124** | **41–63** |

→ 原報告寫「預約 40–60 h（AI 輔助）／90–130 h（純手寫）」，與上表一致。

### 2.3 其他兩套的主要工時來源

| 系統 | 工時大頭 | 為何較高／較低 |
|---|---|---|
| 線上點餐 80–120 h | 品項選項模型（加料、甜度）15–20 h、購物車與結帳 12–18 h、即時接單看板 10–15 h、**金流 Sandbox + Webhook 驗章 + 退款 20–30 h**、電子發票 10–15 h、測試 15–20 h | 整合型工作占比最高（AI 係數 0.7–0.9），且有外部審核等待 |

## 3. LINE 預約 vs 現成預約 SaaS

### 3.1 比較對象
| 代號 | 方案 | 類型 |
|---|---|---|
| A | **自建 LINE 預約**（本案） | LINE 內開啟的預約網頁 + 店家官方帳號推播 |
| B | LINE 官方帳號人工回覆 + Google 表單 | 目前多數小店的實際做法（基準線） |
| C | Google 日曆「預約時段」 | 通用預約頁 |
| D | SimplyBook.me / Setmore 類國際通用 SaaS | 國際通用預約 SaaS |
| E | Fresha 類美業平台 | 免月費、靠金流／新客抽成 |
| F | 台灣在地預約／訂位 SaaS（如 inline 等；美業類多家，需市調） | 在地 SaaS |

### 3.2 功能比較

| 功能 | A 自建 LINE 預約 | B 人工+表單 | C Google 預約 | D 國際 SaaS | E 美業平台 | F 在地 SaaS |
|---|---|---|---|---|---|---|
| 在 LINE 內完成預約，不跳出 | ✅ | ⚠️ 跳表單 | ❌ | ❌（多為外部連結） | ❌ | ⚠️ 視廠商 |
| 用店家自己的官方帳號發提醒 | ✅ | ⚠️ 人工 | ❌（Email） | ❌（Email/SMS） | ❌（平台通知） | ⚠️ 視廠商，部分支援 |
| 即時顯示可預約時段、防重複 | ✅ | ❌ | ✅ | ✅ | ✅ | ✅ |
| 指定服務人員 | ✅ | ⚠️ | ⚠️ 有限 | ✅ | ✅ | ✅ |
| 爽約紀錄 | ✅ | ❌ | ❌ | ⚠️ | ✅ | ⚠️ |
| 繁中介面與在地習慣 | ✅ | ✅ | ✅ | ⚠️ 翻譯品質不一 | ⚠️ | ✅ |
| 線上訂金 | ❌（第二階段不做） | ❌ | ❌ | ✅ | ✅ | ✅ 多數有 |
| 顧客資料歸屬 | ✅ 店家 | ✅ 店家 | ✅ 店家 | ⚠️ 平台 | ⚠️ 平台（可能導流給其他店） | ⚠️ 視合約 |
| 品牌客製 | ✅ 完全 | — | ❌ | ⚠️ | ❌ | ⚠️ |
| 系統成熟度、客服 | ❌ 新系統 | — | ✅ | ✅ | ✅ | ✅ |

### 3.3 成本比較（單店、月費估計 🔍待驗）

| 方案 | 月費估計 | 主要隱性成本 |
|---|---|---|
| A 自建 | 單店分攤：平台約 NT$1,500–2,000（若只服務 1 家店）；服務 10 家以上可降到約 NT$200–400／店；加上店家自付 LINE 方案 NT$0–1,200 | 建置 41–63 h、每月維護人力 |
| B 人工+表單 | NT$0 + LINE 方案 | **店長每天花在回訊息的時間**、漏回、爽約 |
| C Google 預約 | 免費版功能有限；完整功能需 Google Workspace 付費（約 NT$200–450／人） | 無 LINE 提醒、無人員排班 |
| D 國際 SaaS | 免費版有預約數上限；付費約 US$10–60（NT$320–1,900） | 提醒多為 Email/SMS，SMS 另計 |
| E 美業平台 | 月費 0，但金流與新客抽成 | 顧客被平台導流到其他店 |
| F 在地 SaaS | 約 NT$1,000–3,000+ | 綁約、功能依廠商 |

### 3.4 差異化結論
**自建 LINE 預約唯一可防守的差異化是：「整個流程在 LINE 裡完成 + 用店家自己的官方帳號提醒 + 資料歸店家」**，加上後續可以自然延伸到集點。

但必須坦白：
- 如果店家只要「有個預約頁」，**C、D 已經夠用且便宜**，自建沒有優勢。
- 自建的價值只在「LINE 重度使用 + 爽約痛點明顯 + 想累積自己的會員」的店家（美業、工作室、寵物美容等），**單店自建在經濟上不划算，必須累積到多店才成立**。
- 因此第二階段的目的應定位為「**驗證 LINE 內預約體驗是否明顯優於 C／D**」，而不是直接當商品。

## 4. 單店預約 Demo｜3 天最小開發規格

### 4.1 範圍

| ✅ 做 | ❌ 不做 |
|---|---|
| 單一虛構店家「測試美甲工作室」（店家資料寫在設定檔） | 多店家、店家註冊 |
| 3 個服務、2 位服務人員、固定營業時間 | 排班、休假管理介面（直接改資料） |
| 顧客端：選服務 → 選人員（或不指定）→ 選時段 → 確認 | 改期（只做取消） |
| 我的預約：查看、取消 | 金流、訂金 |
| 店家後台：今日／本週預約列表、標記到店／爽約 | 拖拉式行事曆 |
| LINE 登入（LIFF）+ **示範模式登入**（不用 LINE 也能看 Demo） | 集點、會員等級 |
| LINE 通知：預約成功、取消確認；提醒以**後台「手動發送提醒」按鈕**示範 | 自動排程提醒（見 5.1 Vercel Hobby Cron 限制）、Email／SMS |
| 防重複預約（資料庫排他約束） | 正式網域、SEO |

### 4.2 畫面清單（共 6 頁）
1. `/` 店家首頁：店名、服務列表、「立即預約」
2. `/book` 預約流程（3 步驟同頁）
3. `/book/done` 預約完成
4. `/me` 我的預約（含取消）
5. `/admin` 後台預約列表（今日／本週切換、到店／爽約、發送提醒）
6. `/admin/login` 後台登入（Supabase Email 登入，限 1 個測試帳號）

### 4.3 資料表（5 張）
`services`（名稱、時長、價格）、`staff`（名稱）、`business_hours`（星期、起訖）、`customers`（LINE userId 或示範 ID、顯示名稱）、`bookings`（顧客、服務、人員、起訖時間、狀態：已預約／已取消／已到店／爽約）。
`bookings` 以 `(staff_id, 時間區間)` 排他約束防重疊；全部資料表開啟 RLS。

### 4.4 每日排程

| 天 | 產出 | 驗收標準 |
|---|---|---|
| D1 | 專案骨架、資料表與 RLS、假資料匯入、時段計算、顧客預約流程（示範模式登入） | 手機瀏覽器可完成一筆預約；20 個並發請求搶同一時段僅 1 筆成功 |
| D2 | LIFF 登入、我的預約與取消、LINE 預約成功／取消通知 | 測試者在 LINE 內完成預約並於 10 秒內收到通知；iOS、Android 各一台通過 |
| D3 | 後台列表、到店／爽約、手動提醒、RLS 測試、Preview 部署、工時與成本回填報告 | 顧客 A 查不到顧客 B 的預約；未登入無法進後台；產出 Demo 驗證報告 |

### 4.5 交付物
- Demo 預覽網址（受保護，僅限審查方）
- 操作影片或截圖（給無法登入者查看）
- Demo 驗證報告：驗收結果、實際工時 vs 估計、實測 LINE 則數與費用、發現的問題

### 4.6 測試資料與個資規則
- 店家、服務、人員、示範顧客**全部虛構**。
- LINE 實測無可避免會產生測試者本人的 LINE userId 與顯示名稱，視為內部測試資料：僅限已同意的團隊成員、Demo 結束後 **7 天內刪除**、不得匯出。
- 不開放給任何真實顧客或店家使用。

## 5. 免費帳號、預覽部署的安全與費用限制

### 5.2 費用防線（確保 NT$0）
1. **所有帳號都不綁信用卡**：在 Vercel Hobby、Supabase Free、LINE 免費方案上，用量超過上限時服務會被限制或暫停，不會被扣款。（若任何平台註冊時要求綁卡，**停止並回報**，不自行綁定。）
2. 不購買網域，使用平台提供的預設網址。
3. 不啟用任何付費加購（Supabase PITR、Vercel 付費加購功能、LINE 加購則數）。
4. 每日結束前檢查各平台用量頁，記錄在 Demo 報告。

### 5.3 帳號管理
- 帳號以團隊共用的工作信箱註冊（非個人私人帳號），開啟兩步驟驗證。
- 密鑰不貼在聊天、文件或 GitHub；只存在平台的環境變數設定。
- Demo 驗收後：撤銷 LINE token、暫停或刪除 Supabase 專案、刪除 Vercel 部署（或依總指揮指示保留）。

### 5.4 預覽部署的定位
- Preview 網址**不是正式網站**：不綁網域、不公開宣傳、不收集真實顧客資料、頁面顯示「Demo／測試用」標示。

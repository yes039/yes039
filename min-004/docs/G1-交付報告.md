## 1. 這一輪做了什麼

一個手機優先的單一入口。老闆打開就看到示範店的九宮格，點任何一格都有示範成果；往下按「30 秒免費體驗｜換成我的店」，填五個欄位後，九宮格與整條工作流換成他自己的店。

| 令中要求 | G1 實作 |
|---|---|
| 共用底座＋三種產業模板 | `core.js` 一個底座；`salon.js`、`nail.js`、`cafe.js` 三個模板 |
| 九宮格，每格有可點擊的示範成果 | 9 格都會打開成果面板（文案、分鏡表、行事曆、對話模擬、海報版面、漏斗等），不是功能介紹 |
| 05 行銷總監整合九宮格 | 中央格依目標排出「今天最重要的三件任務」，並彙整其他 8 格的狀態 |
| 三種店型明顯差異 | 每個店型各有 4 個痛點、4 個行銷目標、不同的客服情境與轉真人條件、不同的會員觸發天數、不同的成效漏斗與客單價、不同的示範案例流程（見第 3 節） |
| 先看 Demo | 打開即顯示示範店，示範案例的 7 個步驟全部已完成可閱讀 |
| 換成我的店（五欄、免登入、免留資料） | 店型、店名、主打、客群、目標；主打與客群有建議可點選 |
| AI 員工開始工作 | 依序跑 7 個步驟並逐步顯示成果：目標 → 文案 → 短影音 → PO 文 → LINE 客服 →（店型加值步驟）→ 成效 |
| 成果展示 | 四份可複製的成果包（文案、短影音企劃、發布計畫、客服回覆）、一次複製全部、9:16 成果卡圖片 |
| 商業轉換三個下一步 | 自己學、代管、整套導入，各自對應方案 A／B／C，並可複製需求摘要 |
| 套餐 A／B／C | 每個方案都列出交付範圍、人工審核責任、平台費用、可自動化程度；價格標示「尚未定價」 |
| 標示模板生成／規則式示範 | 每一格與每個工作流步驟都標示「模板生成」「規則式示範」「模擬排程」「模擬數據」 |
| 不啟用真實發布、LINE 自動回覆、付費 API、廣告 | 全部沒有串接。「模擬發布」「採用並送出」只改變頁面上的狀態並明確寫「未連平台」 |

另外加了兩個為驗收核心設計的元件：

- **委派意願**：看完成果後，讓老闆勾選「哪些工作願意先交給 AI」，並依選擇建議起點方案。這直接量測驗收核心第 3 題。
- **測試者面板**：頁尾可展開，即時顯示四個驗收問題的計數與事件紀錄，可複製 JSON。

## 2. 技術架構

```
min-004/demo/
├── index.html                 頁面結構與樣式（手機優先，深淺色主題）
└── js/
    ├── core.js                共用底座（不含任何產業內容）
    ├── industries/
    │   ├── salon.js           A｜美髮沙龍
    │   ├── nail.js            B｜美甲工作室
    │   └── cafe.js            C｜咖啡廳
    └── plans.js               套餐與下一步（共用）
```

**模組化方式**

- 九宮格的 9 個角色定義在底座（`M.MODULES`），所有產業共用同一組位置與名稱。
- 產業模板只回傳「內容積木」：`copy`、`list`、`kv`、`table`、`tasks`、`calendar`、`chat`、`funnel`、`posters`、`json`、`note`。底座負責把積木畫成畫面、轉成可複製的純文字、放進成果卡。
- 每個產業模板提供：示範店資料、痛點、表單建議值、4 個行銷目標（每個含原因、優惠、短影音開場、CTA、成功指標）、工作流步驟順序、9 個模組函式。
- 新增產業＝新增一個檔案＋一行 `<script>`，底座不改。

**資料流**

```
輸入（示範店或表單） → buildCtx（店名、主打、客群、目標、固定亂數種子）
  → 8 個模組各自產出積木 → 行銷總監彙整 → 畫九宮格／工作流／成果包／成果卡
```

模擬數字用「店名＋主打＋目標」算出固定亂數，同一家店每次看到的數字一樣。

**安全與隱私**

- 使用者輸入一律以文字節點顯示，不經過 innerHTML（已測試 HTML 注入）。
- 不送出任何網路請求（只有 Google Fonts 字型）。
- 事件紀錄只存在該瀏覽器的 localStorage，且不含店名、主打、客群等自由輸入內容，只記錄長度與選項。

**影音生產介面（VID100／LibTV）**

短影音員工每次都會產出一份 `min004.video_job.v0` 工單（主題、9:16、30 秒、每個分鏡的畫面與字幕、`human_review_required: true`、`paid_generation: false`），在面板中可展開檢視。G2 接上後，這份工單就是送進影音生產流程的格式。本輪不呼叫任何生成服務。

## 3. 三種店型的差異（不只換店名、圖片、顏色）

| | 美髮沙龍 | 美甲工作室 | 咖啡廳 |

| 4 個目標 | 填滿平日空檔、新客首次體驗、老客回流、新作品曝光 | 季節新品、新客首次體驗、節日活動、顧客回訪 | 下午離峰補位、新品上市、甜點搭售、會員回流 |

| 廣告範圍 | 周邊 3 公里 | 周邊 3 公里 | 周邊 1.5 公里，投放時段 11:30–15:00 |

## 5. G2 真實 AI 與平台串接建議

原則：**先換「生成」，再換「發布」；先建議模式，再自動化。** 每一步都保留人工確認。

### 5.1 建議順序

| 順序 | 項目 | 做法 | 為什麼先做 |
|---|---|---|---|
| 1 | 文案、短影音腳本、會員訊息改用真實模型 | 底座積木格式不變；每個模組改成「產業模板＝提示詞＋輸出格式」，模型回傳同樣的積木 JSON。建議以 Claude（如 claude-sonnet-5-5 處理一般文案、claude-opus-5-5 處理行銷總監彙整）為主，以結構化輸出約束格式 | 直接回答驗收核心第 2 題「成果能不能用」，風險最低 |
| 2 | 店家資料卡 | 讓店家補價格表、營業時間、服務時長、不可說的宣稱，生成時一併帶入 | 現在的價格與時間是範例值，真實使用一定要換 |
| 3 | 事件後端 | 把 `M.track` 改成送到後端（格式見 6.2），開始跨裝置統計四個驗收問題 | 讓驗收數字可以集中看 |
| 4 | LINE 官方帳號（建議模式） | 接 Messaging API Webhook：顧客訊息進來 → AI 產生建議回覆 → 推到店員的確認介面 → 店員按送出才回。客訴、過敏、退款等關鍵字一律轉真人，不產生回覆 | 客服是老闆最有感的格子，但出錯代價最高，所以先只給建議 |
| 5 | 社群排程（IG／FB） | 經 Meta Graph API 建立排程貼文；仍需店家在確認介面核准。G1 的行事曆狀態欄位可直接沿用 | 平台審核與權杖管理較繁瑣，放在生成穩定之後 |
| 6 | 影音生產（VID100／LibTV） | 以 G1 的 `min004.video_job.v0` 工單送出；付費生成需店家授權與每月額度上限；成片回到 PO 文員工的待審清單 | 成本最高，等前面驗證有需求再開 |
| 7 | 成效數據 | IG／FB Insights、LINE 訊息統計、店家 POS 或預約系統匯出 | 取代模擬漏斗 |
| 8 | 廣告 | 先只產出企劃與素材，由店家自己投放；代操另案處理 | 涉及預算，最後才碰 |

### 5.2 G2 必須先決定的事

- 店家資料與顧客訊息的保存位置、保存期間、刪除方式。
- 模型輸出的審核責任劃分（對應方案 A／B／C 的「人工審核責任」欄位）。
- 自動回覆的開放門檻：建議用「建議回覆被店員原封不動採用的比例」連續兩週超過一個門檻，且店家書面授權，才對特定常見問題開放自動回覆。
- 每月 AI 與影音生成的成本上限，以及超過時的處理方式。

### 5.3 G2 建議驗收

- 10 家真實店家（每店型至少 3 家）完成「換成我的店」並實際發出至少 1 則內容。
- 文案被店家「不修改或小修改後使用」的比例。
- LINE 建議回覆被採用的比例、轉真人的比例。
- 四個驗收問題的轉換率（見測試報告第 3 節）。

## 6. MIN-003 V1.2 整合方案（提案，未修改 V1.2）

本 repo 中找不到 MIN-003 V1.2 與 R-001 的規格文件，所以 G1 **沒有引用、也沒有修改** V1.2 的任何欄位。以下是 G1 目前的做法與建議的對接方式，請 GPT／總指揮對照 V1.2 確認後再實作。

### 6.1 推薦夥伴與歸因

- G1 現況：沒有推薦夥伴欄位。發布環境的連結只能帶 `#店型`，無法帶 `?ref=` 參數。
- 建議：G2 架在自有網域後，入口沿用 V1.2 的推薦夥伴參數與歸因窗口；`demo_view` 事件帶上 V1.2 定義的夥伴代碼欄位；歸因規則（首次或最後一次接觸、有效天數）完全依 V1.2，不另訂。

### 6.2 事件

G1 已記錄的事件（每筆含 `ts`、`event`、`session_id`、`industry`、`mode`、`props`）：

| 事件 | 時機 | 主要欄位 | 對應驗收核心 |
|---|---|---|---|
| `demo_view` | 打開頁面 | landing 店型 | — |
| `industry_switch` | 切換示範店型 | to | — |
| `grid_cell_open` | 打開九宮格任一格 | module、from | — |
| `try_start` | 點「換成我的店」 | — | 1 |
| `try_submit` | 送出表單 | goal、店名長度、是否用建議值 | 1 |

### 6.3 同意

- G1 現況：不收集個人資料，所以沒有同意流程；畫面上說明「輸入內容只在這個瀏覽器使用」。
- 建議：G2 在兩個時點觸發 V1.2 的同意流程：(1) 店家要求顧問聯繫、留下聯絡方式時；(2) 店家授權串接 LINE／IG／FB 時。同意文字、版本號、紀錄欄位直接沿用 V1.2。

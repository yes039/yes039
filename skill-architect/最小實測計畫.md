# SK-01／02／03 最小實測計畫（草案 v0.1，待核准）

> 目的：用最小成本確認六項能力在 Claude Code 上**真的可行**，同時找出規格書寫錯的地方。
> 原則：唯讀、本機快照、可回復。**核准前不執行任何一步。**

---

## 1. 範圍與環境

| 項目 | 內容 |
|---|---|
| 執行位置 | Claude Code 雲端 session（本 repo 的分支 `claude/claude-code-skills-architecture-kzs0de`） |
| 資料 | 「未玉欣珍_AI店東_001_營運資料」4 張工作表，**唯讀**下載並存成 CSV，放在 session scratchpad 的 `fixtures/`，不進 repo |
| 技能與子代理檔 | 核准後才建立。建議建在 scratchpad 的模擬專案目錄，以 `--add-dir` 或該目錄為工作目錄載入，不寫進本 repo 的 `.claude/` |
| 不做 | 寫回 Google Sheets、呼叫 LINE 或 OCR、部署 Cloudflare 或 Manus、修改儀表板、開啟 Agent Teams |
| 時間與成本 | 預估 1 個 session、約 30–45 分鐘。子代理同時在場 ≤ 4 |

## 2. 測試需求（一句話）

> 「產出玉欣珍 9/1–9/9 戰情摘要：營收、採購支出、單據積壓、資料品質異常。」

### 2.1 標準答案（我已用原始資料先算好，作為 SK-03 對照）

| 指標 | 標準答案 | 來源 |
|---|---|---|
| 9/3 營收、訂單數、客單價 | 59,942 元、220 單、272.46 元 | 工作表1（全形數字，須先轉半形） |
| 已入帳採購實付合計 | 18,450 元 | 採購主表實付 3,900＋14,550 |
| 對帳不變式 | 主表實付合計 = 暫存單據「已入帳」`total_amount` 合計 = 18,450 | 兩張表交叉核對 |
| 主表「總價＋稅」口徑 | 3,714＋9,238＋4,619＋186＋693 = 18,450（相符） | 若有人把第 4 列再補算一次稅金就會錯 |
| 待確認積壓 | 3 張、5,700 元（1,200＋1,800＋2,700） | 暫存單據狀態＝待確認 |
| 應排除的測試資料 | R-TEST-001、R-TEST-002，以及「測試食品行」2 張 | 測試列 |

> 注意：3 張待確認中有 2 張是「測試食品行」。計入或排除，必須在成果單**明確寫出口徑**。這是故意留的判斷題。

### 2.2 已知陷阱（SK-03 必須抓到 ≥ 5 個）

| # | 陷阱 | 預期報出方式 |
|---|---|---|
| P1 | 工作表1 為全形數字 | 標為資料品質異常，並說明已正規化 |
| P2 | 主表同一張單拆兩列，稅金和實付只寫在第一列 | 指出口徑風險，合計不能重複計算 |
| P3 | 測試列混入暫存單據 | 列出並排除，或明確說明口徑 |
| P4 | OCR 把買方讀成「王欣珍」、品項讀成「炸」 | 標為待人工確認 |
| P5 | 3 張待確認單據沒有入主表 | 列入積壓清單 |
| P6 | 主表第 2 列品類空白 | 標為欄位缺漏 |

## 3. 測試案例

| ID | 測什麼 | 能力 | 步驟 | 通過標準 |
|---|---|---|---|---|
| **T1** | SK-01 拆解 | ①④ | `/sk-01-decompose` 加上 §2 需求和 fixtures 路徑 | 拆解單格式合格；3–6 張卡；營收、採購、單據稽核分屬不同卡；至少 2 張卡同屬一個 `parallel_group`；相依無環；把任一張卡的 `brief` 單獨交給新子代理，不需回問就能執行（抽 1 張實驗） |
| **T2** | SK-02 派工與平行 | ②③④ | `/sk-02-dispatch` 加上 T1 產出 | 同一組的卡在同一回合派出（看派工紀錄時間戳）；子代理只拿到自己的卡；主對話只收摘要；每張卡最終狀態為 DONE、BLOCKED 或 FAIL |
| **T3** | SK-02 整合 | ⑤ | 檢查整合成果單 | 數字全部可追溯到卡 ID 和快照列；§2.1 的數字全對；測試資料的口徑有寫明 |
| **T4** | SK-03 驗收（正常件） | ⑥ | 對 T3 的成果單執行 `/sk-03-verify` | 判 `PASS` 或 `PASS_WITH_NOTES`；P1–P6 至少抓到 5 個；每個檢查項都有證據列 |
| **T5** | SK-03 驗收（故障件）與失敗處理 | ⑥ | (a) 把成果單的採購合計改成 18,900 再驗；(b) 給一張讀不存在檔案的卡，觀察 SK-02 | (a) 必須判 `FAIL`，指出 18,900 ≠ 18,450 並附來源列；(b) SK-02 重派 1 次後標 `BLOCKED`，其他卡不受影響，整合單標明缺口 |

**全程紀律檢查**（每個案例結束後都做）：

- `git status` 乾淨（本 repo 沒有被改動）。
- 試算表的 Drive `modifiedTime` 和實測前相同（沒有寫回）。
- 子代理工具呼叫中沒有 `Write`、`Edit` 或 Drive 寫入；若有被擋下的嘗試，要記錄下來。

## 4. 量測與紀錄

每次實測產出一份 `實測報告.md`（放 scratchpad，核准後才進 repo），內容包含：

| 欄位 | 內容 |
|---|---|
| 每案判定 | T1–T5 各自 PASS 或 FAIL，附證據 |
| 陷阱命中率 | P1–P6 的命中數（例如 5/6） |
| 平行證據 | 同組卡的派出時間 |
| 隔離證據 | 主對話收到的內容長度與子代理實際讀取量的對照 |
| 成本 | 子代理數、總回合數、大約耗時 |
| 規格修正清單 | 實測中發現規格寫錯或不可行之處，以及建議修法 |

## 5. 判定與下一步

| 結果 | 下一步 |
|---|---|
| T1–T5 全過 | 提案把三個技能和子代理定義正式放進 `.claude/`，另開 PR，再次等待核准 |
| T4 或 T5 失敗（驗收官放水或誤殺） | 先修 SK-03 判準，重測 T4、T5，不擴大範圍 |
| T2 平行沒成立 | 檢查是派工 prompt 的問題還是工具限制，必要時改為循序並記錄 |
| frontmatter 欄位不被支援 | 依實際版本調整，並在規格書標註版本差異 |

**核准後才會做的事**（依序）：① 唯讀下載快照；② 在 scratchpad 建立技能和子代理檔；③ 執行 T1–T5；④ 交實測報告。

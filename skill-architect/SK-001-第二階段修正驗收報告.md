### 2.2 玉欣珍的積壓口徑：案件說明本身有缺口

兩次執行都把「尚未入帳」定義為狀態不是已入帳、也不是已作廢，所以包含 1 張「已確認」的測試單（350 元），主口徑為 4 張／6,050 元；排除測試單的對照為 3 張／5,700 元。SK-03 獨立重算也得到 4／6,050。

- 這不是第一階段那種「把已入帳算進去」的錯誤。依字面語意，「已確認」確實還沒入帳。
- 是我原先的標準答案（只算「待確認」）**超出了案件說明**；案件說明沒有定義各狀態的意義，也沒有說測試資料要不要排除。
- 兩次結果完全一致，符合「同資料同結果」。
- **試點前必須補上**：CASE 模板要有「狀態定義」和「測試資料處理」兩個欄位，由店家或主管填寫，不交給 AI 推斷。

### 2.3 新發現：共因錯誤（最重要的剩餘風險）

v0.2a 的讀書會案件中，執行端和 SK-03 都用 `tabcalc count status=報名` 計算有效報名，兩邊都算出 6 人，漏掉重複報名的去重，所以 SK-03 判 PASS。諷刺的是，同一份 profile 已經偵測到這筆重複（F3）。

- **教訓**：確定性工具保證「算得對」，不保證「算對的東西」。驗收端和執行端用同一套工具、同一份規則時，會犯同樣的錯。
- **已做修正**：`--distinct` 去重、自然鍵強制去重、F3 交叉檢核。v0.2b 的 2 次都正確。
- **仍不足**：只驗證 1 輪，也沒有建立能專門偵測共因錯誤的故障件。

## 4. 剩餘風險

1. **共因錯誤**（§2.3）：驗收端和執行端仍共用工具與規則。可行的降低方式是讓 SK-03 加做不變式檢查，例如「總收款＝可對應＋退款＋無法對應」、「去重前後差額＝F3 筆數」。這屬於下一階段，本次未做。
2. **最終版覆蓋不足**：v0.2b 只重跑讀書會 2 個案件；玉欣珍和 3 件故障件仍停在 v0.2a 的結果。
3. **CASE 模板缺狀態定義**（§2.2），口徑仍可能因各案件需求寫法而不同。
4. **hook 誤擋**：正則參數裡的 `$`（例如 `"d~^2026$"`）會被擋，子代理改寫後才通過，每次流程多出 1–8 次重試。這是成本問題，不影響安全。
5. **隔離層級**：仍是 Claude Code 應用層（權限加 hook），不是作業系統沙箱。
6. **樣本數**：每個案件 1–2 次，正確率只能當參考，不足以做統計結論。
7. **CSV 來源**：由 Drive 唯讀 API 的表格內容轉存成 CSV，不是 xlsx 原檔逐格轉換。

## 3. 逐題回答

| 問題 | 路徑 A：V5.0 | 路徑 B：Codex |
|---|---|---|
| 是否為不同發布路徑 | 是 | 是 |
| API／瀏覽器／其他 | 官方 API | 瀏覽器自動化（擴充功能操作已登入的網頁） |
| 定時自動或人工 | 設計上是定時自動（Facebook 端排程）；**未實測** | 實測兩次都要人工介入 |
| 電腦須開機 | 不需要 | **需要**：電腦開機、Codex 在跑 |
| 瀏覽器須登入 | 不需要 | **需要**：Chrome 的 Facebook 保持登入，擴充功能權限保持開啟 |
| 排程逾時 | 不會延後：Facebook 準時發，或排程當下就失敗並顯示錯誤（例如時間少於 10 分鐘、超過 30 天 🟡、權杖失效） | **會**：實測晚 3.5 小時；逾時就被審核擋下，要人工確認 |
| 預定與實際時間紀錄 | 日曆存預定時間；「已發布」狀態要開日曆或按「確認發布狀態」才更新；**不記錄實際發出時間**，只記貼文網址 | 只在 Codex 對話中看到預定 20:00、啟動 23:30；D 槽紀錄未提供 |
| 能否確認 Facebook 端網址與狀態 | 可以：API 回傳貼文 ID，同步後取得 `permalink_url` 與 `is_published` | 目前只有 Codex 的連結文字。**C 無法連到 Facebook 核對**（本環境擋下 facebook.com），需你補網址 |

## 4. 重複發布、漏發與逾時補發：風險與防範

| 風險 | 路徑 A：V5.0 | 路徑 B：Codex | 建議做法（不論哪條路徑） |
|---|---|---|---|
| **重複發布** | 低：一篇日曆貼文只會有一個 Facebook 排程 ID；改內容時會先刪舊排程再重排 | **高**：補發與原排程可能都執行；本次靠「移除一次性排程」避免 | 每篇有唯一作品編號；發之前先到粉專或社團確認有沒有同編號的貼文；發完立刻記下網址 |
| **漏發** | 低（由 Facebook 端執行）；但權杖失效時排程會失敗，要開日曆才看得到 | **高**：電腦關機、睡眠、Codex 沒開、登入失效都會漏，而且沒有主動通知 | 預定時間後 30 分鐘內人工核對一次；漏發就走「補發」 |
| **逾時補發** | 不適用 | 本次 3.5 小時後才補發，內容時效可能已過 | 事先訂好容許延遲（例如 30 分鐘）；超過就改期，不直接補發；補發前要人工確認 |
| **帳號安全** | 權杖只存在 Cloudflare；可隨時撤銷應用程式授權 | 自動化操作的是你的個人登入；被判定為自動化或垃圾訊息時，**個人帳號受限會連帶影響你管理的粉專與社團** | 交付給客戶的方案不使用瀏覽器自動化 |

## 5. 哪條路徑適合交付給一般小店老闆

| 排名 | 路徑 | 理由 | 限制 |
|---|---|---|---|
| **1（建議）** | **Facebook 原生排程**：粉專用 Meta Business Suite，自有社團用社團內建排程（管理員本人操作） | 官方功能、Facebook 準時執行、不用電腦開機、零額外工具、零帳號風險；跟 V-MAP 003 的 A2、OA4 一致 | 每篇要人工排程一次（約 2 分鐘）；社團排程最遠多久只有二手資料 🟡 |
| 2（選配） | V5.0 粉專 API 排程 | 文案產生到排程在同一個系統完成；官方 API | **尚未實測**；需要建 Meta 應用程式與權杖，老闆難以自行維護；只支援粉專 |
| 3（不建議交付） | Codex 瀏覽器自動化 | 能發社團、能上傳圖卡 | 電腦須開機、要保持登入、會延遲、要人工確認；有平台條款與帳號風險；需要 Codex 與擴充功能，教學與維護成本高 |

文宣兵交付規格（03 文件第 5 節）維持不變：**交付稿件，發布由人執行或交給 Facebook 原生排程**。
Codex 路徑目前只建議 Shen 自用，且要人工核對；**不列入 A、B 方案的交付**。
